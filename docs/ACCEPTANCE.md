# smurg acceptance checklist (Prototype)

Every acceptance criterion of SPEC.md R1–R9 and R11, the criteria of the v0.5.0 flow (family T) and the security
points of v0.5.0 (table S), the automated tests that cover each, and its status. This file is
the checklist for the rest of the project: when a feature changes, its rows change in the same change as the tests.
R10 is a launch-phase requirement (SPEC marks it as launch phase, not Prototype) and is not listed. The criteria are
given here in English; SPEC.md holds the original zh-TW wording, under the same criterion ids.

**Hard gate (SPEC §0):** R3. Every one of its criteria is `covered` by a named automated test.

**R5 (the guest sandbox), SPEC's other hard gate, was withdrawn by the project owner on 2026-10-01**, together with the
sandbox parts of R9 and the guest-session parts of R4 (ARCHITECTURE §11 D-15): guests no longer have agents of their
own, there is no guest sandbox, no guest Claude login or API key. Instead the host can give a member the role
Agent access (`agent`), whose sessions run AS THE HOST (the host's account and Claude Code login, on the host's
computer, no sandbox). SPEC.md is the owner's and is not edited; the withdrawn rows below say `withdrawn` and keep what
they covered as the record. The new role has rows of its own under R2 ("R2 (D-15)") and R9.

**v0.5.0 (the owner's brief of 2026-10-05, `docs/design/v0.5.0/`; protocol 4) changed what a session is.** An agent
session is a conversation: Claude Code runs in its structured mode, without a PTY (ARCHITECTURE §11 D-16). A plain
terminal session keeps its PTY and everything it had. Work is organised in topics: a shared discussion, a spec, a
plan of work items, one execution session per item, a result report per item. The brief supersedes SPEC's wording of
R4 and R6 where it is about agents (D-16 to D-23); SPEC.md is still not edited. In this file: the R4 and R6 rows are
rewritten (R4.1 is about terminals; a suggestion goes to an agent session and is never pasted into a terminal), rows
elsewhere that named the removed behaviour say what replaced it, the flow has a family of its own ("T topics flow")
and the design's security points have a table ("S security points of v0.5.0").

## Status legend

| Status | Meaning |
|---|---|
| `covered` | Automated tests run in `pnpm test` and pass. A criterion with several parts is split into rows (R1.2a, R1.2b, …), one status each. |
| `partly` | Automated tests cover part of the criterion; the row says what is left and why. |
| `manual` | Cannot be automated in this repository (the row gives the reason); checked by hand before a release. |
| `withdrawn` | Withdrawn by the project owner on 2026-10-01 (ARCHITECTURE §11 D-15); the row keeps what it covered. Its tests are removed with the code. |

The lint `tests/lint/acceptance-refs.test.ts` checks every reference of this file against the tree: the file must
exist and each quoted title must be in it. While v0.5.0 was being built a row could name a test that was not written
yet, as long as `tests/lint/pending-v050.ts` listed it; the release gate (below) accepts none.

## How to run the gate

```sh
source scripts/env.sh     # Node 22 LTS + the repo's pnpm; leave TMPDIR as it is
pnpm check                # type check of every package, then every vitest project; exit 0 = green
SMURG_RELEASE_GATE=1 pnpm check   # the same, for a release: nothing may be pending (below)
```

- **The release gate (v0.5.0).** With `SMURG_RELEASE_GATE=1` the gate also fails while anything is still on a pending
  list: `tests/lint/pending-v050.ts` (references of this file to tests that are not written yet, and parts of
  cross-package tests that are skipped), `packages/daemon/test/fixtures/pending-v050.ts` (daemon modules and service
  slots that are still stubs) and `packages/daemon/test/fixtures/wire-text-owners.ts` (wire texts nothing produces
  yet). All three must be empty. Without the variable the pending entries are skipped and everything else runs.
  Since 0.5.1 the release gate also needs the published executables and this tree's build: without
  `SMURG_PREVIOUS_BINARIES` and `SMURG_SEA_BINARY` it fails in `@smurg/cli`, because a release must not pass without
  the upgrade from the published executables (row U11; `docs/RELEASING.md` §4.5 step 1 has the command).
- **Agents in the gate are a stand-in.** A test that needs an agent uses the in-memory fake of the agent runtime
  (`packages/daemon/src/core/fakes`) or, where a real process matters, the scripted stand-in `claude`
  (`packages/daemon/src/testing/fake-claude.mjs`: it speaks Claude Code's structured protocol on its pipes, follows a
  scenario file, really writes the files its scripted edits name after running the session's hooks, calls smurg's MCP
  tools, asks questions and permission requests and waits for the answers). The gate therefore needs no Claude Code
  and no account, on a maintainer's machine and in CI alike. No test may reach the `claude` a developer has on
  `PATH` (it would run with that developer's login): the test daemon refuses a session that could
  (`daemon/harness.test.ts` › "never starts the developer's own claude: an agent session needs a hook command, and a
  hook command needs a named claude"), and `scripts/dev-stack.sh` starts nothing without a terminal unless it is told
  which `claude` to use (`packages/cli/test/dev-stack.test.ts`).

## Other ways to run

```sh
source scripts/env.sh
pnpm test                                        # everything (all vitest projects)
pnpm --filter @smurg/e2e test                    # acceptance tests: real relay + real daemon + SDK clients
pnpm --filter @smurg/daemon exec vitest run test/integration   # the real modules together (the release composition)
pnpm exec vitest run --project @smurg/web-smoke  # the BUILT web app in system Chrome, 17 files, 4 to 5 min (skips without Chrome)
SMURG_SMOKE_SHOTS=/some/folder pnpm exec vitest run --project @smurg/web-smoke flow   # the flow smokes, with a picture per step and person
pnpm --filter @smurg/e2e exec vitest run test/r3.e2ee.test.ts --silent=false   # one file, with the measured timings
# every real-claude test of the daemon, with the verified Claude Code (2.1.288) named explicitly. It talks only to the
# repository's fake Anthropic API with a dummy key and its own temporary HOME and config dir; never a real account:
SMURG_TEST_CLAUDE_BIN=/absolute/path/to/claude-2.1.288 \
  pnpm --filter @smurg/daemon exec vitest run test/hooks/claude-e2e.test.ts test/hooks/claude-bash.test.ts \
  test/hooks/claude-failmodes.test.ts test/sessions/agent-claude-real.test.ts test/sessions/trust-claude-real.test.ts
```

Test layers (ARCHITECTURE §10):

- `tests/e2e` (`startStack`): the real relay (local workerd through `@smurg/relay/testing`, with the R3 byte tap), the
  real daemon composing `DEFAULT_FEATURE_MODULES` (production host sockets, JWKS verification of the relay's identity
  tokens) and headless clients (the client SDK's `Connection` over Node's WebSocket, dev login). Temp directories go to
  the fork's `TMPDIR` (removed by the project's global teardown); the daemon gets a fake home.
- `packages/daemon/test/integration`: the REAL modules together (`createTestDaemon` without `modules`), real SDK clients
  over the in-memory relay, the real `smurg hook` entry, real PTYs and the real CLI.
- `packages/daemon/test/<module>`: each module's acceptance tests with real clients (some with fakes of the other

## R4 sessions: terminals and agent conversations

Since v0.5.0 (ARCHITECTURE §11 D-16) there are two kinds of session. A **terminal session** is a shell in a PTY on
the host, as before: R4.1 and R4.2a are about it. An **agent session** is a conversation with Claude Code in its
structured mode. It has no screen, so there is nothing to attach a terminal to: `smurg attach` lists agent sessions
and says where they open, and attaches terminals only. What SPEC asks of a session that outlives its viewers becomes,
for a conversation, that it is complete for whoever opens it later (R4.2b).

## T topics flow (v0.5.0)

The owner's flow of v0.5.0: a topic, its shared discussion with questions and votes, the spec, the plan and who is
responsible, one execution session per work item, permission requests, result reports and their review, the inbox,
the sessions view. The criteria and the titles of their tests are the ones `docs/design/v0.5.0/DESIGN.md` §8 fixed.

**What this family was verified against.** The flow is verified against a scripted stand-in model: the fakes and
the stand-in `claude` of "How to run the gate" play the agent in every test, and real Claude Code 2.1.288 runs only
against the repository's fake Anthropic API. No real Claude account was used by the team at any point (the owner's
decision), so no row says anything about what a real model writes, asks or decides. The prompts, the questions an
agent asks and the reports it writes may need tuning after the owner has tried the flow with a real account.

How the rows are proven, in four layers. (1) Each daemon module (the agent runtime, conversation, topics, inbox,
worktrees) has its rows in its own tests: against the shared fakes of the other modules, and the agent runtime
against the stand-in `claude`. (2) The modules together, as the release composes them and with nothing faked but the
model (the stand-in `claude` through the real runner, the real `smurg hook` and `smurg mcp`, real git): four people
as SDK clients go through a free session, a whole topic, a restart and a member's removal in
`daemon/integration/release-flow.session.test.ts`, `daemon/integration/release-flow.topic.test.ts` › "discussion,
spec, revision, plan, split, Start, items in worktrees, reports, reviews, merges, a conflict, complete, archive",
`daemon/integration/release-flow.restart.test.ts` and `daemon/integration/release-flow.members.test.ts` (and
`daemon/integration/release-composition.test.ts` › "a free agent session end to end: …"); four more stories of the
same kind hold what an independent review of v0.5.0 found and what was fixed for it:
`daemon/integration/release-flow.items.test.ts` (an item merged before its review, and one whose process died before
a restart), `daemon/integration/release-flow.people.test.ts` (a member who becomes a Viewer; a session whose start
is refused), `daemon/integration/release-flow.guard.test.ts` › "the release composition: a folder is everything
below it" and `daemon/integration/release-flow.scripts.test.ts` › "the release composition: the scripts a confirmed
hook runs". (3) The same flow over the real relay with SDK clients: `t.topic-flow.test.ts` › "T topics flow: one
topic through the real relay, five SDK clients and the stand-in claude" (seven steps that are one story: a topic
from its creation to its plan, Start, a member who reloads and one who joins late, a long conversation, a restart of
the host's smurg, reports and merges with a conflict, and what the relay carried). (4) The built app in real
browsers on the real relay: the two flow smokes the rows name ("Other ways to run" above). The design fixed five
titles for tests of the agent runtime under `daemon/sessions/agent/`; that package named its files and tests
differently, and the rows (T1.5, T2.1, T4.2, T4.3, T8.1) name the tests it has.

## S security points of v0.5.0

The security review of the design (`docs/design/v0.5.0/DESIGN.md` §7), point by point and in short: the threat, what
v0.5.0 answers, and the tests of that answer that are in the tree now. The trust model is unchanged (ARCHITECTURE §2,
§11 D-15): sessions run as the host, unsandboxed; a member with agent access is trusted like the host's own account;
Editors and Viewers are not. The rule the review added: what smurg promises about an agent's limits is enforced by
smurg's own code (the tool gate, the pin of a Start, the functions that clean text), and Claude Code's permission
system is the second layer. `SECURITY.md` says the same for users. S5 is written as the owner decided it (decision
Q7 of `docs/design/v0.5.0/OWNER-DECISIONS.md`), not as the design's default.

## Known gaps

- **v0.5.1: what the rule "a published version's files are read by every later one" does not reach yet**
  (ARCHITECTURE §7.1, "What 0.5.1 could not repair"; rows U1 to U19 above). A refusal for the version carries no
  numbers, so the member's command and the page infer which side is older. The control socket's status names no
  version, so `smurg status` beside a `smurg host` of 0.4.0 that still runs shows its usual lines. `smurg.columns.<id>`
  in the browser is written without a check of its version. A link of another role than the member's is refused with
  the words of a dead link (the host guide's §9.4 says what the member does). A deploy of the relay without the
  previous build's files leaves open 0.5.0 tabs without a notice. The fixtures hold no shared folder:
  what a start makes of kept worktrees and pending merge requests when their folders are there was tried by hand
  on the real 0.4.0 state and is in no test. The upgrade with the published executables (U11) is skipped by a plain
  gate and required by a release's, and its last run used a build of tag v0.5.0 in the place of the published 0.5.0
  file. The tools that made the fixtures are
  not in the repository (their READMEs say how each was made). Going back to an older smurg is not supported, and
  nothing tests it. The steps of the host guide's §9.4 were run through the command on the 0.4.0 fixture (U8), not
  by a host on a workspace of their own.
- **v0.5.0 was verified without a real model.** Every agent in the gate is the scripted stand-in `claude`, and real
  Claude Code 2.1.288 ran only against the repository's fake Anthropic API; no real Claude account was used ("T topics
  flow" above). What a real model writes, asks and decides in this flow is not covered by any row.
- **Real Claude Code was tested on macOS only, and only against the fake API, never against the real model**: the
  VM and CI have no Claude Code ("Linux verification"). The floor and the one verified version is 2.1.288; smurg
  refuses to start an agent session on an older one.
- **v0.5.0: nothing waits on a pending list** (`tests/lint/pending-v050.ts` and the two lists of the daemon are
  empty, and `SMURG_RELEASE_GATE=1` refuses an entry). Rows that say `partly` say what is left: R6.2 ("Edit and
  accept" is not clicked in a real browser), T2.1 and T4.2 (their real-Claude runs need a `claude` 2.1.288).
- **Limits of v0.5.0 that an independent review left as limits** (what a host has to know of them is in
  `docs/HOSTING.md` §10.8 and the sections it names; the last two below are about the look of one bar and about a
  test):
  - No subagents: the tool that starts one is in no session's list and the gate refuses it under both of its names
    (S15). Turning them on is an open question for the owner.
  - The tool gate's look at a shell command (row G10, S10) reads what the command names. A program that names none
    of the scripts a confirmed project setting runs (a build, a script that rewrites another) is not seen before it
    runs; the trust gate's watch notices the changed script afterwards, parks the folder's sessions and asks the host
    again. A hook that fires in between runs the changed script once. And the reading has bounds: a write to a
    script that stands five shells deep, or in a line that names more than 256 places, asks whoever may allow
    commands, not the host alone.
  - `admin.transcript.redact` replaces one conversation event. A question, a permission request and a suggestion are
    not events (the conversation points to a card), so their content, the excerpts of inbox notes, a report's
    follow-up questions and the audit log's full texts stay; deleting the topic removes all but the audit log (S8).
  - Ending an agent session ends what its commands left running (`daemon/sessions/kill.test.ts` › "R3-04 what the
    commands of an AGENT session left running"). On macOS a job of one of Apple's own binaries that was orphaned at
    once is found only if the 2-second scan saw it while its shell still ran (the class of §11 D-3).
  - A topic's folder swapped by a program outside smurg is read again at once (the pin and an armed item follow),
    but the Start dialog does not list it as changed outside smurg; a change of `SPEC.md` or `PLAN.md` itself from
    outside is listed (`daemon/topics/hand-edits-folder.test.ts` › "what the WATCHER says about a folder names
    nobody …").
  - A link whose words only look like the address of another place is drawn as an ordinary link, with its real
    destination behind hover and keyboard focus, in the cases the reading of S14 does not cover: a bare ASCII word
    under an ending that is not one of about fifty (`amazon.in`, `github.lol`); a "dot" that Unicode's compatibility
    form does not turn into one (U+0660, U+A4F8, U+06D4, U+0702, the raised dots U+00B7, U+2219, U+22C5, U+30FB,
    U+2027); a character that is drawn with almost no width and is not one of Unicode's default ignorable ones
    before the dot (U+FFFC, U+200A; U+007F in a file); a name written backwards behind U+202E in a file the daemon
    does not clean; and a look-alike name under an unlisted ending that the link's own path repeats (the file-name
    exception). Whether every link should show its host is an open question for the owner (`docs/JOINING.md` §5
    says what a reader can rely on).
  - Typing in a `SPEC.md` that is over its time budget costs up to two budgets a keystroke until every section
    that is slow to format is remembered (measured on a hostile 990 KiB spec of 62 sections: two tasks of 0.42 s
    for each of the first 26 keystrokes, then none); and what waits behind the piece a text ran out on is formatted
    as one task of the whole budget, not in slices.
  - The status bar of a conversation with two buttons and no second sentence puts the buttons on a line of their
    own in a column of 460 to 620 px (320 to 500 px in zh-TW) although they would fit beside the sentence.
  - The cut of long runs of marks before two names are ordered (`compareText` in the web app) is in the code and
    listed by `web/test/text-cost.test.tsx`, but no test turns red without it: the pair the test compares has a
    common beginning the collator skips.
- **D-15 (2026-10-01): a member with agent access runs sessions as the host**, with the host's account and Claude
  Code login and no sandbox: by design nothing confines what such a session does (ARCHITECTURE §12, `docs/HOSTING.md`
  §5.1). R5, R4.3, R4.4, R9.1, R9.2 (for agents) and SPEC §13 items 2–5 are `withdrawn`; the role's own rows are
  "R2 (D-15)" and "R9 (D-15)".
- Linux: the whole gate runs on Ubuntu 24.04 (VM and CI, "Linux verification" above); terminals get SIGWINCH on resize
  and Ctrl-C interrupts the foreground program, not the session. Not run on Linux: a real `claude` (the hooks, and
  since v0.5.0 the agent runtime's real-Claude suite, unless the VM has a Linux build of Claude Code 2.1.288),
  keep-awake from a local desktop session, the installer on a fresh machine.
- Browsers other than Chrome (Safari/WebKit's wrapped device keys, Firefox) were not run.
- R7.2 at the full 10 GB is manual. R1.1: releases are built for the four platforms and hosted, but the timing on a
  fresh machine has not been measured, and the macOS executables carry only an ad hoc signature (`docs/RELEASING.md`).
- A real `claude` driving the web editor's lock banner is not automated (the banner is driven through the lock manager,
  as the hook socket does; the real `claude`'s lock requests are proven at the daemon level).
- R8.5: an agent's Bash edits are attributed (§11 D-13, on by default) except when two
  sessions' shell commands that could both have written the file overlap (then "Outside program", by design). Within
  5 s of a person's autosave the files module attributes any change of that file to that person (also the side a
  conflict names).
- Text typed while the host was down, merged back after a daemon restart: against a real daemon restart this is not
  automated; it is proven one layer down.
- The hook matrix of `daemon/hooks/claude-failmodes.test.ts` has no MultiEdit case that runs: Claude Code 2.1.288,
  the one verified version, no longer has that tool (since v0.5.0 the hook is registered for every tool, so a tool
  that comes back, or a new one, is gated too).
