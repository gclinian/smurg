# 主人指南：用 smurg 分享資料夾

這份文件寫給**主人**：在自己的電腦上執行 `smurg host`，把一個專案資料夾分享給組員的人。組員請看
[組員指南](JOINING.md)。這份指南的英文版：[English](../HOSTING.md)。

第一次用 smurg？先看[快速上手](QUICKSTART.md)。

你的團隊在工作區裡做的事：你開一個**主題**（一個功能或一件工作），大家一起和 agent 討論，agent 會出選擇題讓大家決定，
再寫出 spec；接著 agent 把 spec 變成一份由工作項目組成的計畫，每個工作項目由一個 agent 在自己的 git worktree 裡完成，
報告寫著完成且驗證過的項目由 smurg 合併到你的資料夾（除非你每個項目都自己合併，§10.3），最後由團隊驗收成果。agent 就是 Claude Code，在你的電腦上用你的 Claude 帳號執行。整個流程的每一步
寫在組員指南裡；這份指南講的是這些事對你和你的電腦代表什麼。

## 1. 安裝

一行指令安裝（macOS：Apple Silicon、Intel；Linux：x64、arm64，glibc）：

```sh
curl -fsSL https://smurg.ai/install.sh | sh
```

`https://smurg.ai/install.sh` 只是轉到 `https://downloads.smurg.ai/latest/install.sh`，也就是最新版本的安裝程式；
安裝程式從 `https://downloads.smurg.ai/v<版本>/` 下載那個版本的執行檔，並核對同一個版本的 `SHA256SUMS`。要安裝特定
版本，直接執行那個版本的安裝程式：`curl -fsSL https://downloads.smurg.ai/v<版本>/install.sh | sh`（`<版本>` 換成
`X.Y.Z` 形式的版本號）。

安裝程式會下載這台電腦的單一執行檔（不需要 Node.js），**只在 sha256 與這個版本的 `SHA256SUMS` 相符時**安裝到
`~/.local/bin/smurg`，並告訴你怎麼把 `~/.local/bin` 加到 `PATH`（加好之後要重新開一個終端機）。在每個平台上它都只安裝
這個執行檔：不需要 `sudo`，也不安裝任何系統套件。

- macOS 的執行檔沒有 Apple 的開發者簽章（只有 ad-hoc 簽章）。安裝程式驗證 sha256 之後，會移除 macOS 的隔離標記
  （quarantine），所以第一次執行時不會被 Gatekeeper 擋下。請用上面的指令安裝，不要用瀏覽器下載執行檔再手動執行。
- 更新：`smurg update`；移除：`smurg uninstall`（都在 §9）。`smurg --version` 顯示目前的版本。
- 重新執行一次安裝指令，也會把最新版本裝在現有的版本上。如果要被換掉的 smurg 正在分享工作區，安裝程式會停下來，
  什麼都不裝：請先停止分享（`smurg stop`），和 `smurg update` 一樣（§9.1）。
  `curl -fsSL https://smurg.ai/install.sh | sh -s -- --force` 會照樣安裝；這時還在執行的 `smurg host` 必須停止後再重新啟動。
- 要執行 agent，這台電腦還需要 `claude` 指令（Claude Code **2.1.288 以上**），而且要**已經登入**你的 Claude 帳號：
  每個 agent session 都用這台電腦上的這個登入，不論它是替工作區裡的誰工作（§4、§5.1）。Claude Code 版本太舊時，agent
  session 會被拒絕；版本比這個 smurg 驗證過的還新時，agent session 照常執行，你會收到一則通知說明這件事。是哪一種，
  `smurg status` 會顯示（§7）。
- 這台電腦有 git 2.42 以上的版本時，工作項目會在 worktree 裡執行，各有一份 diff：報告寫著完成且驗證過時由 smurg 合併（或由你
  自己合併，§10.3）。沒有 `.git` 的資料夾
  也可以：smurg 會在 `.smurg` 裡保存它自己的版本紀錄（§10.2）。沒有 git 時，工作項目會一次一個直接在資料夾裡執行，
  沒有 diff，也無法復原（§10.2）。
- **語言**：smurg 的介面有英文和繁體中文，每個人看到的是自己的語言。`smurg` 指令依這台電腦的語言設定選擇
  （`LC_ALL`、`LC_MESSAGES`、`LANG`；在 macOS 上這三個都沒有設定時，看系統的語言），不是繁體中文就用英文；要自己指定，
  設定環境變數 `SMURG_LANG=zh-TW` 或 `SMURG_LANG=en`。網頁版依瀏覽器的語言，也可以用畫面上的語言選單切換。這份指南
  引用的是繁體中文介面的文字；你的組員用英文介面時，看到的是同一句話的英文。
- smurg 是開放原始碼軟體，以 MIT 授權條款釋出：條款見 https://smurg.ai/zh-TW/license/，原始碼在
  https://github.com/gclinian/smurg。執行檔裡的第三方軟體與它們的授權：`smurg licenses`，或
  https://smurg.ai/third-party-notices.txt。

## 2. 登入 relay

relay 是 smurg 的伺服器：負責登入，並在你的電腦和組員之間轉送**加密後**的資料。邀請連結、網頁版的工作區也都在
relay 的網址上。

```sh
smurg login          # 不加 --relay 時使用公用 relay（§2.1）
```

終端機會印出一個網址和一組代碼：

```text
在任何裝置（電腦或手機）打開：
  https://app.smurg.ai/device
輸入代碼：WDJB-MJHT   （10 分鐘內有效）
```

1. 在**任何一台裝置**（這台電腦、另一台電腦或手機都可以）的瀏覽器打開這個網址，用你的 Google 帳號登入。
2. 輸入終端機上的代碼（大小寫和「-」都可以省略），按「下一步」。
3. 頁面會列出要登入的帳號、這次登入是從哪裡要求的（IP 位址和大概的位置）和時間。**只有你自己剛在終端機執行
   `smurg login` 時才按「允許」；如果是別人給你這個代碼，請按「拒絕」。** 按「允許」之後，終端機在幾秒內顯示「已登入」。

- 在有桌面的電腦上，smurg 也會自動用這台電腦的瀏覽器打開這個網址。網址裡沒有代碼：代碼一定要你自己輸入。
- **透過 SSH 使用、或在沒有桌面的伺服器上**：做法完全一樣，用你面前的電腦或手機打開網址、輸入代碼，不需要轉接埠或其他
  設定（smurg 不會在那台電腦上打開瀏覽器）。這時頁面上的 IP 位址和位置是那台遠端電腦的。
- `--no-browser` 或環境變數 `SMURG_NO_BROWSER=1`：不自動打開瀏覽器，只印網址和代碼。
- 代碼 10 分鐘內有效，只能用一次。過期了或按了「拒絕」，重新執行 `smurg login` 就好；等待時按 Ctrl-C 可以取消。
- 不要把代碼告訴別人，也不要輸入別人給你的代碼：輸入並按「允許」，就是讓執行那個 `smurg login` 的電腦用你的帳號登入
  （7 天內有效）。
- 可以跳過這一步：`smurg host` 發現還沒登入時會先請你登入（同樣是網址和代碼）。`smurg host` 開始分享前，如果登入在
  24 小時內就會過期，也會先請你重新登入。
- 登入資料存在 `~/.smurg/credentials.json`（權限 0600），依 relay 網址分開記錄。

### 2.1 公用 relay（預設）

smurg 的維護者在 Cloudflare 上架設了一個所有人都可以使用的 relay：https://app.smurg.ai（也是網頁版：組員的邀請連結
和工作區都在這個網址上）。發佈版的 smurg 預設就用它，**你不需要部署任何東西**，只要有 Google 帳號（主人和組員都用 Google 登入）。

**relay 看得到什麼**：

- 看不到：檔案內容、檔名、和 agent 的對話、終端機畫面、你或組員輸入的指令、邀請連結的密鑰、任何金鑰。這些在你的電腦和
  組員的瀏覽器（或 CLI）之間端對端加密，relay 只轉送加密後的資料。
- 看得到：每條連線是**哪個 Google 帳號**（帳號 ID、名稱、大頭貼；登入時 Google 也會給 relay 你的 email，只有帳號沒有
  名稱時拿來當顯示名稱）、**從哪個 IP 位址連線**、連到哪個工作區代碼，以及每筆資料的大小和時間。從這些可以看出誰和誰
  在什麼時候一起工作、傳了多少資料。
- 保存：每個工作區的代碼和它的主人是哪個帳號。登入本身不保存（relay 的登入是有效 7 天的簽章權杖）；只有用代碼登入
  `smurg` 時，relay 會保存那次登入最多 10 分鐘（代碼、執行 `smurg login` 的電腦的 IP 位址與大概位置，顯示在確認頁上），
  完成或過期就刪除。為了擋下猜代碼和大量登入，relay 也會保存 IP 位址與帳號的雜湊值和次數，10 分鐘後刪除。
- 架設者（smurg 的維護者）和 Cloudflare 因此也可能知道上面「看得到」的內容。不能接受的話，可以自己架設 relay（§2.2）：
  那時看得到這些的是你和你的 Cloudflare 帳號。
- 網頁版也由 relay 提供。和所有在瀏覽器裡做的端對端加密一樣，提供被竄改的網頁版的 relay，可以讀到那個瀏覽器解密的
  內容和它的金鑰。`smurg` 指令不會從 relay 載入程式碼。

**免費方案的限制**：公用 relay 用 Cloudflare 的免費方案，**所有使用公用 relay 的人共用**每天固定的用量：

- 用量的單位是連線、每幾秒一次的「主人還在嗎」檢查，以及轉送的每一筆資料。最耗用量的是**大家一起看正在輸出文字的
  agent，或正在大量輸出的終端機**；只是開著工作區、偶爾編輯，用得很少。
- 一天的用量用完時，**所有人**（不只你）都可能連不上：新的連線和登入會失敗，已經連著的也可能中斷，直到台灣時間
  **早上 8 點**（UTC 0 點）重新計算。這時主人的終端機會提示與 relay 的連線中斷，組員看到「無法連上伺服器」，瀏覽器也
  可能顯示 Cloudflare 的錯誤頁（Error 1027）。
- 維護者會觀察用量，必要時改用付費方案。整班同時長時間使用、或不能接受中斷時，請自己架設 relay（§2.2）：它有自己的
  用量，不受其他人影響。

### 2.2 其他 relay（`--relay`）

relay 的原始碼是公開的（MIT），所以**你可以自己架設 relay**：它是一個 Cloudflare Worker，用自己的 Cloudflare 帳號（免費方案
即可）和自己的 Google OAuth client 就能部署，網頁版也由它提供。步驟在 relay 的說明文件
[`apps/relay/README.md`](../../apps/relay/README.md#self-hosting-on-workersdev)（英文）。架設好之後，用 `--relay` 指定它：

```sh
smurg login --relay https://relay.example.org      # 換成你的 relay 的網址；出現哪些登入按鈕由那個 relay 決定
smurg host ~/projects/my-app                        # 用上次登入的 relay
```

選擇 relay 的順序：`--relay`、環境變數 `SMURG_RELAY_URL`、上次登入的 relay，都沒有時才用公用 relay。要換回
公用 relay：`smurg login --relay https://app.smurg.ai`。你印出的邀請連結會指向你用的 relay，組員不需要另外設定。relay 也
提供網頁版，而網頁版、你的 `smurg` 和每個 `smurg attach` 必須使用同一個通訊協定版本（§9.1）：每次更新 smurg 之後、
重新分享之前，都要重新部署你自己的 relay。

## 3. 分享

```sh
smurg host ~/projects/my-app
```

`smurg host` 在前景執行，終端機只印出兩個連結：

```
smurg 正在分享「my-app」

你的連結（只給你自己用）：
  https://app.smurg.ai/join/ws_…#k=…&s=…

給組員的連結（用私訊傳給他們，7 天內有效）：
  https://app.smurg.ai/join/ws_…#k=…&s=…

按 Ctrl-C 停止分享。
```

- **你的連結**：在瀏覽器以主人身分打開工作區。只能用一次，7 天內有效；不要給別人。
- **給組員的連結**：預設角色是「可編輯」（editor），7 天內有效、不限次數。連結裡 `#` 之後就是密鑰：
  請用私訊傳給組員，不要貼在公開的地方。選項：`--role agent|editor|viewer`、`--expires 12h`、`--max-uses 3`、
  `--name 顯示名稱`；你用了別的角色或次數上限時，這一行也會寫出來。**`--role agent`（「可使用 agent」）之前請先讀
  §5.1**：拿到這個連結的人可以用你的電腦和你的 Claude 帳號執行任何指令。

終端機不會重複這份指南的說明：**第一次分享之前請先讀 §4**；「可使用 agent」角色、agent 自己能做什麼、你自己的 Claude Code
設定算不算數，都在 §5；一個主題需要你做什麼在 §10。分享中的詳細狀態用 `smurg status` 查看（§7）：daemon 金鑰指紋、
Claude Code 與 agent session、防止睡眠、紀錄檔的位置。終端機只在你需要處理的時候提示：**無法防止睡眠**（§6）、與 relay
的連線中斷、relay 拒絕你的登入、狀態檔寫不進磁碟（§7）；有新版本時，連結下面會多一行「有新版本…」（§9.1）。更新之後
第一次分享時，連結上面會有一行說明工作區已經沿用（§9.2）；更新到 0.6.0 之後，還會多一行說明 agent 現在以自動模式執行
（§5.2）；更新到 0.7.0 之後，再多一行說明工作項目現在會自動合併（§9.2）。你讓 agent 什麼都不問的期間，每次啟動時連結上面
都會有一行說明（§5.2）。連結下面，在任何東西繼續之前，會有一行說明哪些主題會自己繼續（§10.5）。

**daemon 金鑰指紋**：組員第一次加入時，可以用其他管道（當面、電話）和你核對這組指紋，確認沒有人（包括 relay）冒充你。
指紋用 `smurg status` 查看（「daemon 金鑰指紋：」那一行）。

角色：「旁觀」（`viewer`）只能看；「可編輯」（`editor`）可以編輯檔案、對 agent 的選擇題投票和留言、檢視結果報告、對 agent
提出建議；「可使用 agent」（`agent`）還可以開始主題和工作項目、傳訊息給 agent、允許 agent 請求執行的事，並**以你的身分**
在你的電腦上開終端機（§5.1）。之後可以在網頁的主人控制台管理成員、角色、邀請與 session，查看操作紀錄。

之後再分享同一個資料夾時，它的主題和上次的 agent session 都還在，對話也還在，計畫會從停下的地方自己繼續，有人暫停的
計畫除外（§7、§10.5）。

## 4. 分享前必讀

`smurg host` 不會在終端機提醒這些事，請在第一次分享之前讀完。

- **資料夾裡的檔案，每個成員都看得到**（旁觀者也一樣），例如 `.env`、設定檔。組員在網頁和 CLI 裡看不到、也下載不到的
  只有：smurg 自己的 `.smurg/`、所有 `.git` 資料夾、`.envrc`，以及你個人的 Claude Code 設定（`.claude/settings.local.json`、
  `CLAUDE.local.md`）。這只限制人看到的。agent 也被要求不去讀這些檔案，Claude Code 會對它自己的工具和指名這些檔案的指令
  執行這條限制；但是你或「可使用 agent」的成員允許的指令是以你的身分執行的，讀得到你的帳號讀得到的任何東西，終端機
  session 也一樣（§5.1）。不要分享放了密碼、金鑰或個人資料的資料夾；也不能分享整個家目錄或包含家目錄的資料夾。
- **每個成員都讀得到和 agent 的每一段對話**，之後才加入的成員也一樣：他們讀得到這個工作區之前的每一段對話，包括已封存
  主題的。主人控制台在你建立邀請連結的地方會這樣說明：
  「新成員可以讀到這個工作區先前的所有對話，包括已封存主題的對話。」
  而且 agent 讀到的任何東西，它都可能說出來：寫在回答裡、spec 裡、結果報告裡。smurg 在儲存和顯示之前，會把看起來像常見金鑰或權杖的文字換成 `[masked]`，但這只是盡力而為。不要讓 agent 在
  檔案內容或指令輸出裡有機密的資料夾工作（對話存在哪裡、怎麼刪除，見 §5.4）。
- **整個團隊用的是誰的 Claude 帳號**：每個 agent 都用這台電腦上 `claude` 目前登入的帳號，替組員工作時也一樣；用量和費用
  都算在你身上。**個人的 Claude 訂閱（Pro 或 Max）只供你自己使用。** Anthropic 的條款不允許把個人帳號提供給其他人使用；
  多人使用時，請讓 Claude Code 改用 API 金鑰、Team 或 Enterprise 方案，或雲端供應商登入。smurg 不會阻止你，但會在三個
  地方告訴你。開始主題的對話框會對你這樣說（組員在那裡只會讀到 agent 用的是主人的帳號）：
  「個人的 Claude 訂閱（Pro 或 Max）只供你自己使用。有其他人在這裡使用 agent 時，請改用 API 金鑰、Team 或 Enterprise 方案。」
  主人控制台的安全須知會再說一次：
  「這裡的 agent 使用你的 Claude Code 登入。個人的 Pro 或 Max 訂閱只供你自己使用：有其他人在這裡使用 agent 時，請改用 API 金鑰、Team 或 Enterprise 方案。」
  另外，Claude Code 回報的是 Pro 或 Max 的登入、而工作區裡除了你還有其他成員時，agent 第一次啟動的那一刻，你（只有你）
  會在網頁上收到一則通知。這則通知整個工作區只會出現一次，不是每次分享都有；當時你沒有開著任何視窗的話，它會在你下次打開
  工作區時送到。在你按「知道了」或關掉頁面之前，它也會留在主人控制台的 session 清單上方：
  「這裡的 agent 使用你個人的 Claude 訂閱。Anthropic 的條款不允許把個人帳號提供給其他人使用；多人使用請改用 API 金鑰、Team 或 Enterprise 方案，或雲端供應商。」
- **所有 agent session 都不在沙盒裡。** 預設情況下，agent 以 Claude Code 的自動模式執行：由 Claude Code 的檢查決定哪些
  指令可以執行，agent 在自己資料夾裡改檔案和簡單的檔案指令不經過這道檢查，smurg 自己也會在少數幾種指令之前先問或拒絕
  （§5.2）。不論執行的是什麼，都是以你的作業系統帳號執行的。agent 會讀到組員寫入或修改的檔案，還有 spec 和計畫，而每個
  「可編輯」的成員都能改這兩個檔案：檔案裡可能藏有要 agent 執行的指示（prompt injection），而 Claude Code 的檢查是模型的
  判斷，不是一道牆。對資料夾或團隊沒有把握時，請選會先問的模式（§5.2）。被問到時，允許指令之前先讀過，設定一律允許某一類
  指令之前先想清楚，並留意最近被組員修改過的檔案。「可使用 agent」的組員也能回答這些請求。
- **工作項目會自己合併到你的資料夾。** 預設情況下，工作項目的報告寫著完成且驗證過時，smurg 會替你合併它，不會先有人讀過
  diff：在儲存庫裡，它會成為你的分支上的一個提交。報告裡的驗證是 agent 自己說的；影響了某個工作項目的 agent 的 prompt
  injection，也會這樣進到你的資料夾。你可以關掉這件事（在主人控制台的設定裡，把「合併工作項目」選成
  「每個項目都由我自己合併」），也可以復原合併過的項目（§10.3）。
- **只把「可使用 agent」給你完全信任的人**（§5.1）：這個角色可以讓 agent 在你的電腦上執行任何指令、讀你的家目錄、
  用你的 Claude 帳號。其他組員用「可編輯」就能參與：一起編輯、投票、留言、檢視報告、對 agent 提出建議。
- 組員只能在 `smurg host` 執行、而且你的電腦連線時使用這個工作區。
- 可編輯以上的組員可以在分享的資料夾裡新增或修改 `.gitmodules`、`.gitconfig`、`.bashrc`、`.zshrc`、`.profile` 這類
  檔案（git 和 shell 不會從專案資料夾執行它們）。執行 `git submodule update` 之前，請看一下 `.gitmodules` 是否被改過。
  Claude Code 會當成設定或指示來讀的檔案（`.claude/`、`.mcp.json`、`CLAUDE.md`），透過 smurg 只有你能改（§5.3）。
- **資料夾裡只要有只有你能改的檔案，組員就不能重新命名或刪除這個資料夾**，不論那個檔案在第幾層：`.claude`、`.git`、
  `.vscode`、`.idea`、`.mcp.json`、`.envrc`、`CLAUDE.md` 或 `CLAUDE.local.md`。移動資料夾，就等於把這些檔案一起移走。
  你可能想不到的資料夾也會這樣，例如 `node_modules`：只要裡面有某個套件附了 `CLAUDE.md` 或 `.vscode` 資料夾。組員會看到
  「只有主人可以修改這個路徑」
  這樣的資料夾請你自己重新命名或刪除。smurg 是實際去看磁碟上這個資料夾的內容來判斷的；裡面超過 100,000 個項目的資料夾會
  直接被拒絕，不再往下看。

## 5. 「可使用 agent」角色與 agent 的 shell 指令

### 5.1 「可使用 agent」角色（請先讀）

「可使用 agent」（`agent`）是你能給組員的最高角色。有這個角色的組員可以：

- **開始主題和工作項目**，並在你的電腦上開 agent session 和終端機 session，在主工作區或 worktree 裡工作；
- **傳訊息給任何 agent**、停止它，並**允許 agent 請求執行的事**（§5.2），可以只允許一次，也可以一律允許某一類指令；
- **選擇任何 agent session 和主題的工作項目的模型與權限模式**（§5.2）：你的 Claude Code 提供的任何模型，以及「什麼都不問」
  以外的任何模式；
- 在**任何**終端機 session 裡直接輸入，包括你自己開的和其他組員開的；
- 採用或不採用任何 agent session 收到的建議、用自己的話回答 agent 的選擇題，並請你合併任何一個 worktree（合併由你作主：
  預設情況下，工作項目的報告寫著完成且驗證過的，由 smurg 替你合併，§10.3）；
- **決定沒有合併的工作項目要怎麼處理**（「就這樣合併」、「略過這個項目…」），以及暫停計畫。

這些 session **以你的身分在你的電腦上執行**，和你自己在終端機裡開的沒有差別：

- **沒有沙盒**：用你的作業系統帳號、你的家目錄（包括 `~/.claude` 裡你的設定、`CLAUDE.md` 和記憶）和你的環境變數。
- **用你自己的 Claude Code 登入**：每個 agent 都用這台電腦上 `claude` 目前登入的帳號（你的訂閱或你的 API key），
  **用量和費用都算在你身上**（哪一種帳號適合多人使用，見 §4）。組員不需要、也沒有辦法改用他們自己的 Claude 帳號或
  API key。
- worktree 只是工作的位置，不是保護：在 worktree 裡開的 session 一樣以你的身分執行。

**風險**：給某人「可使用 agent」，等於讓他在你的電腦上使用你的帳號。他可以：

- 讓 agent 或終端機**在你的電腦上執行任何指令**：安裝或刪除程式、修改或刪除分享資料夾以外的檔案、連到任何網路位置；
- **讀取你的家目錄**：例如 `~/.ssh` 的金鑰、其他專案、各種程式和雲端服務的登入資料，以及分享資料夾裡組員本來看不到
  的 `.git`、`.envrc`；
- **使用你的 Claude 帳號**：用掉你的訂閱額度，或讓你的 API key 產生費用。他也能選擇他開的或操作的 session 使用的模型：
  在某些方案上，有的模型會從用量額度扣款，而在 agent session 裡，Claude Code 扣款之前不會先問（主人控制台的設定會列出
  使用這種模型的 session）；
- **透過工作項目進到你的資料夾**：他開始的工作項目，或他對它的 agent 說過話的工作項目，報告寫著完成且驗證過時會自己合併到
  你的資料夾，不會先有人讀過 diff，除非你關掉自動合併（§10.3）。

smurg 沒有辦法限制這些事：「可使用 agent」的組員可以開終端機，也可以允許 agent 請求的任何事。工作區裡每個人都即時看得到
每個 session，操作紀錄記下每個 session 是誰開的、每一則傳給 agent 的訊息、每一次對權限請求的回答，但這些只能讓你事後
知道發生了什麼。**只把這個角色給你完全信任的人**，例如你願意把自己已經登入的電腦交給他使用的人。其他組員請用
「可編輯」：他們可以一起編輯檔案、對 agent 的選擇題投票，並對 agent 提出建議，由你或有「可使用 agent」的人決定要不要採用。

在預設的自動模式下（§5.2），任何 agent session（包括組員的）的指令，只要碰到分享資料夾以外的地方，都是在 Claude Code 的
檢查允許之後就執行；smurg 仍然會先問的地方，見 §5.2。

- **給**：分享時用 `smurg host <資料夾> --role agent`，印出的組員連結就是「可使用 agent」的連結；或在分享中從網頁的
  主人控制台建立這個角色的邀請連結、把成員的角色改成「可使用 agent」（控制台會先顯示同樣的風險提醒，按「我了解…」
  才會建立或變更）。
- **收回**：在主人控制台把角色改回「可編輯」或「旁觀」，或移出那位成員（控制台上的按鈕叫「踢出」）。他不能再開始任何事、傳訊息給 agent 或回答請求。
  他開的終端機和不屬於主題的 agent session 會立刻結束。他開始的主題的 session **會轉給你**：你只是改角色時，它們繼續
  執行；你把他移出時，它們會先被停止。他保留下來的 worktree（連同裡面的修改）也會轉給你：他不能再移除它們，裡面的修改要
  怎麼處理由你決定。他設定的東西會跟著他一起消失：他設為一律允許的指令類型、他開始但還沒開工的工作項目、他選的、沒有比 session 原本會
  跟隨的更嚴格的權限模式、他選的可能從用量額度扣款的模型、他傳出去而 agent 還沒讀到的訊息（§10.6）。**這只收回他在 smurg 裡的權限**，他之前以你的身分做過的事不會跟著
  消失：請看下面「收回之後」的清單。
- 開始之前請確認 `claude` 已經在這台電腦上登入（在你自己的終端機執行 `claude` 並登入）。agent session 裡沒有辦法登入：
  Claude Code 沒有登入時，agent session 會這樣顯示，並等你在自己的終端機登入（§8）。

**收回之後**：他有「可使用 agent」的期間，可以用你的帳號讀過、複製過你讀得到的任何東西，也可以在電腦上留下之後會
自動執行的東西。如果你不再信任他，或不確定他做過什麼，請做完這些事：

1. **換掉工作區的金鑰和邀請連結**：先用 `smurg status` 記下工作區代碼（停止之後 `smurg status` 就不會再列出它），再
   `smurg stop` 停止分享，把 `~/.smurg/workspaces/<工作區代碼>/` 移到別的地方（例如在名稱後面加上 `.old`），然後用
   `smurg host` 重新分享。daemon 金鑰和邀請連結的密鑰都會換新（他可能讀過舊的）；其他組員要用新的邀請連結重新加入。
   - 加入過的組員用新連結時會看到「**主人的電腦金鑰和之前不同**」（網頁和 `smurg attach` 都會先問過才繼續）。請用
     `smurg status` 查看新的 **daemon 金鑰指紋**，用其他管道（當面、電話）告訴他們，讓他們比對過再繼續。
   - 這個工作區的主題、對話和操作紀錄都在你移走的資料夾裡：新的工作區一開始沒有它們。spec、計畫和報告是專案裡的檔案，
     會留著。
   - 舊的 worktree 還留在 `<資料夾>/.smurg/worktrees/`：新的工作區狀態不認得它們，組員看不到，smurg 也不能再合併或
     移除它們。裡面還要的修改請你自己檢查後合併到主工作區，再刪掉這些資料夾。
   - 只停止再重新分享、不移走這個資料夾的話，金鑰和還沒過期的邀請連結都不會變。
   - 新的工作區第一次啟動時，會用一行指出你移走的那個資料夾，開頭是「這個工作區之前的狀態資料夾還放在旁邊」。這一行
     也是寫給照 smurg 0.5.0 的指示移走資料夾的主人看的（§9.4）。你是特意移走的：讓它留在原處，不要移回來（你想換掉的
     金鑰就在裡面），等不再需要裡面的對話和操作紀錄時再刪掉。
2. **換掉 relay 的登入**：`smurg logout`，再 `smurg login`。relay 的登入沒有辦法提前作廢：他如果複製了舊的登入資料
   （`~/.smurg/credentials.json`），在它到期之前（登入後最多 7 天）仍然可以用。
3. **換掉其他登入資料**：Claude Code 的登入（在你的終端機執行 `claude`，`/logout` 再 `/login`；用 API key 的話換一把
   新的）、`~/.ssh` 的金鑰，以及家目錄裡其他程式和雲端服務的登入資料。
4. **檢查會自動執行的地方**，有你不認得的內容就移除：
   - shell 設定檔：`~/.zshrc`、`~/.zprofile`、`~/.bashrc`、`~/.bash_profile`、`~/.profile`；
   - 排程：`crontab -l`；
   - 登入時自動啟動的程式：macOS 的 `~/Library/LaunchAgents/`，Linux 的 systemd 使用者服務（`~/.config/systemd/user/`，
     `systemctl --user list-unit-files`）和 `~/.config/autostart/`；
   - `~/.ssh/authorized_keys`：多出來的金鑰能讓人不經過 smurg 直接登入你的電腦；
   - Claude Code 的設定：`~/.claude/settings.json` 的 `hooks` 和權限規則（你自己的允許規則對這裡的每個 agent 都有效，
     §5.3），以及 `~/.claude/CLAUDE.md`（之後每個 agent 都會照著做）；
   - 你的 git 專案（分享的和其他的）：`.git/hooks/` 裡的腳本，以及會執行程式的 git 設定，例如
     `git config --show-origin --get-regexp 'core\.(fsmonitor|hooksPath|sshCommand)'`（也看 `~/.gitconfig`）；
   - 還在執行的程式：session 結束時 smurg 會結束它找得到的程式，但刻意脫離 session 的程式可能繼續以你的帳號執行，
     也可以透過這台電腦上的控制 socket（`smurg attach` 用的）在任何終端機 session 裡輸入，包括你自己的。不確定的話，
     做完上面的檢查之後重新開機。
5. **紀錄分不出是他還是你**：他透過 session 用你的作業系統帳號做的事，在系統和其他程式的紀錄裡都和你自己做的一樣。
   smurg 的操作紀錄記下 session 是誰開的、每一則傳給 agent 的訊息、每一次對權限請求的回答（連同完整的指令），以及
   agent 沒有經過請求就執行的每一個指令；它不記在終端機 session 裡輸入的內容。這台電腦上的控制 socket（`smurg attach`
   用的）只能用來列出 session 和接上終端機 session，不能拿來以你的名義傳訊息給 agent、回答它們的請求、投票、開始工作、
   改角色、核准合併、踢人或變更設定；可是在收回之前，他仍然可以用你的作業系統帳號做任何你能做的事。

### 5.2 agent 自己能做什麼，什麼要先問

agent 每一次使用工具之前，都會先經過 smurg 自己的檢查。這個檢查在 Claude Code 自己的權限機制之前執行，不論你的
Claude Code 設定允許什麼都有效。之後什麼不用人回答就能執行，要看 session 的**權限模式**和它在哪裡工作：

- **主題的討論 agent** 只讀專案裡的檔案（不包括 §4 提到組員看不到的那些），只能寫這個主題的 `SPEC.md` 和 `PLAN.md`，
  沒有 shell，也沒有網路工具。它的權限是固定的（session 上顯示「可讀程式碼，只能寫 spec 和計畫」）。它用卡片向團隊
  提出選擇題。
- 其他每一個 agent session（工作項目的，以及不屬於主題的 session）的**權限模式**：
  - 「自動：檢查通過就執行」，這是預設。由 Claude Code 決定：agent 在自己資料夾裡改檔案和簡單的檔案指令（`echo … >`、
    `>>`、`mkdir`、`cp`、`mv`、`rm`、`rm -rf <資料夾>`）直接執行，完全不經過檢查；其他每一個指令都要經過 Claude Code 的
    檢查，也就是一個模型對對話和指令的判斷，檢查允許了才執行。被檢查擋下的指令不會執行，對話裡會說明
    （「Claude Code 的檢查擋下了一個指令：…」）；連續擋下三次之後，Claude Code 會用卡片問人。smurg 自己仍然會在少數幾種
    指令之前先問或拒絕（見下面）。
  - 「執行指令前先問」：改檔案直接執行；在 worktree 裡，裡面的唯讀指令和簡單的檔案指令（`ls`、`cat`、`mkdir`、`mv`、
    `cp`）也不用先問。其他的都要先問：任何其他指令、任何網路存取、它的資料夾以外的任何東西。在主工作區裡，它可以直接
    編輯檔案（檔案鎖仍然有效，見組員指南），但每個會寫入的 shell 指令都要先問。
  - 「編輯和執行指令前都先問」：改檔案也要先問。
  - 「什麼都不問」：只有你能選，而且是整個工作區一起（見下面）。
- **誰選哪一個**：工作區的模式由你決定，在主人控制台的設定裡（「agent 不必先問就能做的事」）。你和「可使用 agent」的成員可以
  為一個主題的工作項目（在計畫裡，以及開始對話框裡），或為某一個 session（開它的時候，以及之後在它上方的資訊列）選擇前三種
  裡的另一種。沒有人選過模式的 session 跟隨「工作區預設（…）」；工作項目跟隨「主題的設定」。自動模式的檢查是有代價的：
  「自動模式會多送請求給 Claude 來檢查指令，可能算進你的用量。」（成員看到的是「主人的用量」）。
- **自動模式不檢查什麼**：
  - 不經檢查的那條路：agent 在自己工作的資料夾裡改檔案和簡單的檔案指令，完全不經過檢查。在主工作區裡，它們會立刻改動
    大家共用的資料夾，只有下面 smurg 的兩種情況例外；
  - 分享資料夾以外的指令：任何 session（包括組員的）寫到分享資料夾以外（你的家目錄、其他專案）的指令，只要 Claude Code 的
    檢查允許就會執行。smurg 只對組員的 session、而且只在它讀得出指令寫到哪裡時才會先問（見下面），也只拒絕下面每種模式都
    有效的那些地方，而且只拒絕指名它們的指令；
  - smurg 讀不懂的指令（腳本、直譯器、`sh -c`、變數）：smurg 看不出它們寫到哪裡。在組員開的或開始的 session 裡，smurg 會
    先問你，而且只有你能允許；卡片上會寫
    「smurg 會先問，是因為它看不出組員的 session 的這個指令會寫到哪裡，而在自動模式下，這個指令可能完全不經過檢查就執行。」
    在你自己的 session 裡，這種指令只要 Claude Code 的檢查允許就會執行，而 Claude Code 2.1.288
    對目標是變數的指令（`F=notes.md; rm "$F"`）完全不檢查：這種指令可能在沒有任何人被問的情況下，改到只有你能改的檔案；
  - 讀取：agent 讀得到資料夾裡的每一個檔案，在自動模式下也讀得到 Claude Code 的檢查讓它讀的其他地方，只有組員看不到的
    檔案（§4）和 smurg 的狀態資料夾除外，smurg 會拒絕指名它們的指令；
  - 指令的輸出（檢查看不到它）；
  - 檢查允許過的任何事：那是模型的判斷，不是沙盒。
- **在 worktree 裡**（工作項目，或你在 worktree 裡開的 session）：不經檢查的那條路放行的東西會留在 worktree 裡，結果報告的
  diff 會顯示它。它隨著項目的合併進到主工作區：在預設的自動合併下，項目的報告寫著完成且驗證過時就會合併，不會先有人讀過
  （§10.3）；選「每個項目都由我自己合併」時，要等你讀過 diff。指令在 worktree 以外改的東西，不會出現在那份 diff 裡（見下面
  幾點）。
- **在主工作區裡**（在那裡工作、不屬於主題的 session，以及沒有 git 時的工作項目，§10.2）：在那裡執行的東西會立刻改動
  分享的資料夾。在自動模式下，smurg 會攔下兩種 shell 寫入。組員開的 session 的指令要改只有你能改的檔案（`CLAUDE.md`、
  `.claude/`、`.vscode/`、你確認過的專案設定會執行的腳本、smurg 的 `.smurg`，或裝著這些的資料夾）時，會先問，而且只有你能
  允許；卡片上會寫
  「smurg 會先問，是因為這個指令會改到只有主人能改的檔案，而在自動模式下，沒有其他檢查會在它執行前先問。」
  指令要寫入有人正在輸入的檔案時，會被拒絕，直到對方停下來（agent 會收到英文的說明）。agent 的編輯工具在每種模式下都照
  原來的規則：要等人的檔案鎖，組員的 session 的 agent 也不能改只有你能改的檔案。
- **組員的 session 寫到它自己資料夾以外的地方**：在自動模式下，組員開的或開始的 session（包括組員按開始的工作項目）的
  shell 指令，要寫到這個 session 自己資料夾以外的地方時，會先問，而且只有你能允許。從 worktree 來看，這也包括主資料夾和
  其他工作項目的 worktree；系統的暫存資料夾（`/tmp` 這類）不在此限。卡片上會寫
  「smurg 會先問，是因為組員的 session 的這個指令會寫到它自己資料夾以外的地方，而在自動模式下，沒有其他檢查會在它執行前先問。」
  smurg 只看得到它讀得出來的指令內容。你自己的 session 不會被問：它們能碰到多遠，由你選的模式決定。
- **不論哪種模式，包括「什麼都不問」**，smurg 都會拒絕 agent 編輯這些地方，以及指名這些地方的 shell 指令：分享資料夾的
  `.git`、`.claude/` 和 `.mcp.json`，以及 smurg 自己的版本紀錄（`.smurg/git`），從工作項目的 worktree 也一樣；你的
  `~/.claude`、`~/.claude.json`（以及你設定了 `CLAUDE_CONFIG_DIR` 時它指的資料夾）和你的 `~/.ssh`；smurg 的狀態資料夾
  `~/.smurg`（讀取也不行）；以及 smurg 自己的執行檔，smurg 的每一道檢查都會執行它。這些規則會拒絕編輯工具，以及指名其中
  某個地方的指令。用其他方式碰到它們的指令（腳本、程式、變數、先 `cd`）不會被這些規則拒絕：在自動模式下由 Claude Code 的
  檢查決定，在會先問的模式下會先問，在「什麼都不問」下會直接執行。它們不是沙盒。其他工作項目的 worktree 沒有這樣的規則
  （它就在 session 自己的資料夾旁邊）：組員的工作項目寫到那裡會先問你（見上面），你自己的工作項目寫進另一個項目的 worktree
  的東西，會成為那個項目的變更的一部分，跟著它一起合併，在自動合併下不會先有人讀過。
- **「什麼都不問」**：只有你能選，而且是整個工作區一起，在主人控制台的設定裡選。smurg 會先顯示
  「要讓 agent 什麼都不問嗎？」和下面的警告，要你按下「什麼都不問」才會儲存：
  「這個工作區的每個 agent session 都會以你的身分、在你的電腦上執行每一個指令，沒有沙盒，Claude Code 和 smurg 都不檢查，不論是誰的訊息或哪個檔案讓它這麼做：組員的訊息、有人改過的檔案、agent 讀到的網頁都一樣。仍然有效的只有：討論用的 agent 只寫自己的 spec 和計畫；smurg 會拒絕 agent 編輯 Claude Code 的設定（你的和專案的）、.git、你的 .ssh 資料夾和 smurg 自己的檔案，也會拒絕指名這些地方的指令。用其他方式碰到它們的指令，會以你的身分執行。只有對這個資料夾和團隊完全信任時才選這個。」
  此外仍然有效的：smurg 其他的拒絕（檔案鎖、組員的編輯工具不能改只有你能改的檔案）、不啟動 subagent、不展開 `@路徑`
  （見下面）。smurg 以 root 身分執行時不能選它（那時 Claude Code 會拒絕）。它開著的期間，每個成員都會在工作區的最上面一排
  看到「agent 什麼都不問」，「可使用 agent」的成員仍然可以為主題或 session 選擇更嚴格的模式，而 `smurg host` 每次啟動時都會在
  連結上面印出這一行：

```text
這個工作區的 agent 什麼都不問：每一個指令都以你的身分執行，Claude Code 不檢查，smurg 也不會先問（只剩 smurg 固定的限制）。要改，請在主人控制台的設定裡選其他模式。說明：https://smurg.ai/zh-TW/docs/hosting/#52-agent-自己能做什麼什麼要先問
```

- **改變模式**：更嚴格的模式會立刻套用到執行中的 agent。session 要等它的 agent 重新啟動，才會改成「什麼都不問」：smurg 會
  為它重新啟動待命的 agent。每個 session 的對話裡都會寫出是誰改了它的模式，或是你改了工作區的模式。
- **實際執行的模式不一樣時**：Claude Code 可能用和 smurg 要求的不同的模式執行：沒有自動模式的模型（Claude Code 2.1.288 裡的
  Haiku）、你的或組織的 Claude Code 設定關掉了自動模式（`disableAutoMode`），或關掉了不經詢問就執行（`disableBypassPermissionsMode`）。
  smurg 每一輪都會讀 Claude Code 回報的模式，並且自己退到比較嚴格的一邊：不能用自動模式的 session 會在執行指令前先問
  （「…不能使用自動模式。」），Claude Code 不讓它什麼都不問的 session 則改用自動模式。這時 session 上方的資訊列會顯示
  「Claude Code 實際用的是：…」和原因，對話裡也會說明一次，主人控制台的設定也會說你的 Claude Code 關掉了哪一種模式。
- **Claude Code 會放行、但 smurg 會拒絕的事**：smurg 會拒絕 agent 編輯 Claude Code 的設定（你的和專案的）、`.git` 和
  smurg 自己的檔案，以及指名它們的指令；用其他方式碰到它們的指令，在自動模式下由 Claude Code 的檢查決定，在「什麼都不問」
  下會直接執行。組員開的 session 的 agent 不能用編輯工具改只有你能改的檔案（`CLAUDE.md`、`.vscode/`、`.idea/`），在自動
  模式下，它要改這些檔案的 shell 指令也會先問你（見上面）。
- **這個版本的 agent 不會啟動 subagent。** Claude Code 用來啟動 subagent 的工具不會提供給 agent session，真的被呼叫時
  smurg 也會拒絕；`.claude/agents` 裡的 agent 定義不會被使用。原因：subagent 是照它自己的定義所寫的權限模式工作的，不是
  照 smurg 為這個 session 設定的模式，所以一份定義就可能讓編輯和檔案指令，在一個什麼都要先問的 session 裡不經詢問就執行。
- **訊息沒有辦法把檔案直接交給 agent。** 在你自己的終端機裡，Claude Code 會把你輸入的 `@路徑` 換成那個檔案的內容。在這裡
  不會：smurg 把每一則訊息都當成程式組好的文字送出，所以 `@路徑` 就只是一般文字。檔案只會透過 agent 自己的工具到它手上，
  而那些工具受上面的限制和權限請求管制。想讓 agent 看某個檔案，寫出它的路徑就好：它會自己去讀。
- 你電腦上的 smurg 本身無法回應時（當掉了，或被強制結束），agent 每一次使用工具都會被拒絕，所以不會有無人看管的執行
  （§7）。

**權限請求。** agent 來問的時候（它的模式要它問、smurg 的檢查要它問，或 Claude Code 的檢查連續擋下三個指令），它的對話和
收件夾裡會出現一張卡片，agent 會等待。卡片顯示完整的指令（或是一次編輯的完整 diff，或是工具收到的全部內容）、會在哪裡
執行，以及 Claude Code 提出的理由（請求是 smurg 自己提出的時候，則是 smurg 的理由，見上面和 §5.3）。大到無法完整顯示的
請求會直接被拒絕，絕不截短顯示。顯示的內容不會漏掉任何東西：看不見的字元（隱形或零寬度的字元、會改變文字方向的字元、
控制字元）會寫成看得見的記號，例如在指令裡寫成 `<U+202E>`。很長的指令或 diff 會放在可以捲動的方框裡；卡片會寫出它總共
有幾行，而且要把每個這樣的方框都捲到最後，兩個允許的按鈕才能按：
把要求的內容捲到最後，才能按「允許」。

- **誰可以回答**：你和每一位「可使用 agent」的成員；「可編輯」和「旁觀」的成員看得到請求，但不能回答。session 的負責人
  可以回答時，請求先進他的收件夾；沒有指派負責人、或過了等待時間時（預設 5 分鐘，可以在主人控制台的設定裡改；那個人
  離線時是一分鐘），它會出現在你和每一位「可使用 agent」成員的收件夾裡。先回答的人算數。這項設定是
  「等多久之後也詢問其他人（分鐘）」。
- **回答**：「允許一次」、「一律允許這類」或「拒絕」（可以附上一行說明，告訴 agent 改做什麼）。
- **「一律允許這類」** 只對兩種請求提供：以兩到三個固定的字開頭的指令（例如 `pnpm test`），以及從某一個指定的主機擷取
  內容。shell 和直譯器、會下載並執行程式碼的指令（`pnpm add`、`npx`）、只有一個字的指令、由好幾個指令組成的指令
  （`pnpm test && git push`：一個類型指的是一個指令）、只有你能允許的請求，都不會提供；卡片會說明原因。範圍由你選：
  「在這個 session」或「在這個主題的所有 session」（一個主題允許的類型也列在它的計畫裡，可以在那裡新增和移除）。主題
  允許的類型，只有在另一個 session 正在等的請求剛好是這一類的一個單純指令（沒有串接、管線或重新導向，裡面也沒有變數和
  替換），或是從這一類指定的主機擷取內容、而且網址不超過 2,048 個字元時，才會自己替它回答。agent 改了指令會執行的檔案
  之後，同一類指令仍然包含在內：可以一律執行測試的 agent，可以改一個測試檔再執行它寫的內容。session 的權限選單會列出
  那裡一律允許的類型，每一項都可以移除。新增它的成員被移出或失去「可使用 agent」時，那一項也會自己消失。
- **只有你能允許的請求**：這是在說仍然會先問的那些：會先問的模式的卡片，以及自動模式下 smurg 的檢查提出的卡片（見上面）。
  smurg 認得出會動到專案以外的請求（例如專案以外的檔案）會顯示
  「只有主人可以允許：它會動到共用專案以外的地方。」由好幾個部分組成、又提到 `.claude`、`.git` 或 `.mcp.json` 的指令、會寫到
  你確認過的專案設定的腳本所在位置的指令（§5.3），以及自動模式下上面那些組員的 session 的卡片，也會這樣顯示。這是 smurg
  認得出來的請求的標示，不是一道牆：被允許的指令（被你，或在自動模式下被 Claude Code 的檢查允許）仍然可以碰到你的帳號碰得到
  的任何地方。
- 每一次回答都連同完整的指令記在操作紀錄裡；沒有經過請求就執行的每一個指令也會記下來，執行失敗的也一樣（「agent 執行指令」
  那一筆會寫出模式）。被 Claude Code 的檢查擋下的指令另外有一筆：「Claude Code 的檢查擋下 agent 的指令」。執行過的指令的那
  一筆不會寫是哪一條規則放行的（Claude Code 的檢查、有人設為一律允許的類型、你自己的規則，或 worktree 裡的唯讀指令）；由
  主題的一律允許類型放行的指令另外有自己的一筆，會寫出是哪一類。被 Claude Code 自己的拒絕規則擋下的指令，會被記成執行
  過、而且失敗了（它的結果會寫出被拒絕）。

### 5.3 你自己的 Claude Code：允許規則、MCP 伺服器、專案設定、`CLAUDE.md`

**你自己的允許規則也有效。** 如果你自己的 Claude Code 設定（`~/.claude/settings.json`）已經允許某些指令不經詢問就執行，
這裡的 agent 也一樣被允許，和在你自己的終端機裡完全相同：這樣的指令不會有權限請求，agent 替組員工作時也一樣。smurg
會告訴你一次有哪些規則適用：收件夾裡的「你自己的 Claude Code 規則在這裡也適用」會打開清單；這只是告知，不需要確認
（「這裡的 agent 也會直接執行」）。清單會留在主人控制台的
「我自己的 Claude Code 規則」；`smurg status` 會顯示有幾條適用（§7），你和「可使用 agent」的成員也可以在 session 的
權限選單裡看到清單。smurg 是在 agent 啟動時向 Claude Code 問到這些規則的：第一個 agent session 啟動之前，清單是空的，
`smurg status` 顯示「沒有規則套用到 agent session」。之後出現新的規則時，會再告訴你一次。清單會寫出每條規則的來源：
你的使用者設定、專案的設定（要等你確認過，見下面），或受管理的設定。不想讓某條規則在這裡適用，就把它從你自己的
Claude Code 設定裡移除。不論你的規則是什麼，§5.2 的限制都有效：討論 agent 還是沒有 shell，smurg 會拒絕 agent 編輯
Claude Code 的設定以及指名它們的指令，可能改到專案設定的腳本的指令也還是要先問（見下面）。

**你對自動模式的設定也有效。** 你的 `~/.claude/settings.json` 裡的 `autoMode` 規則（Claude Code 的檢查允許什麼、拒絕
什麼），在這裡的 agent 上和在你自己的終端機裡一樣有效。`disableAutoMode` 會關掉自動模式，`disableBypassPermissionsMode`
會關掉「什麼都不問」，對這裡的每個 agent 都一樣：session 會照 §5.2 說的退回去，主人控制台的設定也會說你的 Claude Code
關掉了哪一種。smurg 不會把任何 `CLAUDE_CODE_*` 環境變數傳給 agent，只有選擇你的服務供應商的那些除外，所以你在自己的
shell 裡設定、會改變自動模式的變數（例如 `CLAUDE_CODE_AUTO_MODE_MODEL`）不會傳到它們那裡。

**你的 MCP 伺服器、連接器和外掛，agent 預設不能用**，除非你在主人控制台的設定裡打開
（「agent 可以使用我自己的和這個專案的 MCP 伺服器」；討論 agent 永遠不能用）。打開之前
請想清楚：任何「可使用 agent」的成員都能指揮的 agent 就可以呼叫這些伺服器（郵件、雲端硬碟、聊天），而它們的回應每個
成員都看得到。打開之後，這類呼叫會是一個顯示工具收到的全部內容的權限請求，而專案自己的 `.mcp.json` 裡的伺服器還需要
下面的確認。

**Claude Code 專案設定。** 分享的資料夾裡可能有它自己的 Claude Code 設定：三個設定檔（`.claude/settings.json`、
`.claude/settings.local.json`、`.mcp.json`），以及 `.claude/` 底下的其他所有東西（agent、skill、指令、規則）。它們可以
執行指令（hook、MCP 伺服器）、變更權限、設定環境變數。在你自己的終端機裡，Claude Code 載入它們之前會先問你是否信任這個
資料夾。smurg 裡的 agent session 不會顯示這個問題，所以改由 smurg 問你：

- 你分享的資料夾裡有你還沒決定的這類設定時，從開始分享起，你（只有你）的收件夾裡就會有一項：
  「Claude Code 專案設定等主人確認」。點它會打開主人控制台裡的檢視。在你決定之前，開始主題的對話框也會給你看同一份
  檢視，標題是「這個資料夾有 Claude Code 專案設定」。組員在你決定之前先開始主題的話，對話框會告訴他：在你確認之前，
  討論不會載入這些設定。你還沒決定、而工作項目已經在 worktree 裡執行時，同一件事會在你的收件夾裡出現好幾次：主工作區
  一次，每個 worktree 各一次。它們說的是同一份內容，決定一次就全部解決。
- **檢視會列出什麼。** 三個設定檔各自會執行的每一個指令、每一條權限規則、每一個環境變數，以及這些指令提到的資料夾裡的
  檔案（也就是它們的腳本），原始檔案點一下就能看。可能把你的 Claude 登入送到別的伺服器的變數會特別標示，會改變執行哪些
  程式的變數（`PATH`、`NODE_OPTIONS` 這類）也一樣。看不見的字元會寫出來，例如寫成 `<U+202E>`。第四項
  「.claude/ 裡的其他內容」會列出 `.claude/` 底下的其他每一個檔案，以及這些檔案自己宣告的東西（hook、允許的工具、
  權限模式）。
- **清單沒有列出全部內容時**，檢視會說明。太長的清單、沒有顯示完整的項目，上方會有一行說明。smurg 追蹤不到會執行哪些
  檔案的指令，下面也會有一行說明，清單上方的說明還會寫出這種指令有幾個，例如
  `smurg 無法得知這些指令裡有 2 個會執行哪些檔案：只有列出的腳本受到保護。`
  這種指令裡，程式本身或交給它的腳本是變數、萬用字元，或指令自己組出來的文字（`sh $SCRIPT`、`eval`）。寫法不像一般人會寫
  的指令也算在內，smurg 不會把它讀完：連續超過十六個包裝用的指令（`env`、`sudo`、`nice`、`timeout`、`command`、
  `exec`、`nohup`、`xargs`；後面接著很長的一個字時，更少就算），或是 `eval`、`sh -c` 一層包一層超過三層。smurg 只能看守它
  列得出來的腳本，所以決定之前請先讀檔案本身。這時要使用這些設定，得多勾選一項：
  「上面的清單沒有列出全部內容。我已經讀過檔案本身。」
- **由你選擇**「使用」或「不載入（agent 不會讀 CLAUDE.md）」。設定可能把你的登入送到別處、或讓 agent 不經詢問就動手時，
  要先勾選你讀過的事項。有些設定照現在的樣子沒有辦法使用，檢視會在「其他設定」的最上面寫出原因：例如 `.claude/`
  底下有連結、那裡超過 2,000 個檔案、腳本超過 20 個，或腳本的名稱裡有反斜線。
- 在你確認之前，agent session 不會載入這些設定，而且依 Claude Code 的做法，也不會載入專案的 `CLAUDE.md`；對話裡會說明：
  「主人尚未確認這個資料夾的 Claude Code 專案設定，這個 session 不會載入它們，也不會載入專案的 CLAUDE.md。」
- **你確認的是內容，不是資料夾。** smurg 會看著這些設定檔、腳本，以及它們上層的資料夾。其中任何一個變了、被換掉或被
  移動（合併進主工作區造成的也算），在那個資料夾工作的 agent 會被停止，之後不會載入這些設定，直到你再看過：
  「這個資料夾的 Claude Code 專案設定有變動，agent 已停止，等主人確認」
- **設定使用期間，腳本由你掌管。** 透過 smurg 只有你能改這些設定檔和腳本：組員不能，agent 的編輯工具不能，組員或工作項目
  提出的合併也不能。指令提到、但還沒有檔案的路徑（選用的腳本，或 `dist/hooks/check.js` 這類建置產物）也用同樣的方式
  看守：透過 smurg 只有你能建立它，而且這個檔案一出現就算是變動。檢視會把這種路徑標成「有提到，但檔案還不存在」。所以
  執行建置產物的 hook，每次建置產生那個檔案之後，都會再問你一次。
- **agent 在這些腳本附近執行的 shell 指令。** 使用中的設定提到腳本的期間，agent 在那個資料夾的每一個 shell 指令，smurg
  都會在執行之前先讀過，「什麼都不問」以外的每種模式都一樣；在工作項目的 worktree 裡和自動模式下也一樣，即使那裡簡單的
  檔案指令平常不用先問。交給另一個 shell 的指令列
  （`sh -c '…'`）會和這一行本身一樣被讀過。遇到下面兩種情況，就會問人；卡片上平常寫 Claude Code 理由的地方，會改用讀的
  人的語言寫出 smurg 的理由。有人設為一律允許的類型不包含這種指令，你自己的允許規則也不包含：它每次都會問。只是讀腳本的
  指令（`cat`、`grep`、`diff`）、在腳本旁邊寫別的檔案的指令，以及沒有提到腳本或它的資料夾的其他任何程式（`npm test`，
  或 git 的 `status`、`diff`、`log`、`add`、`commit`），這項檢查不會管。
  - 指令會寫到腳本所在的位置：腳本本身、它底下的任何東西，或它上層的資料夾
    （`> scripts/lint.sh`、`cp x/lint.sh scripts/`、`mv scripts scripts.old`）；用萬用字元寫、而萬用字元對得上其中之一的
    也算（`rm scripts/*.sh`）。這種請求只有你能允許。卡片上會寫：
    「smurg 會先問，是因為這個指令會更動這個資料夾的 Claude Code 專案設定所執行的腳本所在的位置（腳本本身，或放腳本的資料夾）。這些腳本會以主人的身分執行。」
  - smurg 判斷不出來。檔案指令寫入的位置 smurg 讀不出來：變數、替換、從另一個程式的輸出拿到的檔名（`xargs rm`），或是
    切換到 smurg 不知道的目錄之後寫的相對路徑。某個程式的參數直接寫了腳本或它的資料夾，不論是單獨一個字，還是黏在選項
    後面（`sh scripts/lint.sh`、`sort -oscripts/lint.sh`、`git diff --output=scripts/lint.sh`）。git 那些不必寫出檔名、
    就會把檔案帶進工作目錄的指令（`checkout`、`switch`、`restore`、`reset`、`stash`、`merge`、`rebase`、`pull`、
    `cherry-pick`、`revert`、`apply`、`am`、`clean`）。或是這一行超出 smurg 追蹤的範圍：shell 裡面再包 shell 超過四層、
    切換目錄超過 16 次，或提到的位置超過 256 個。這種請求你和「可使用 agent」的成員都能允許；smurg 追蹤不了的那一行
    即使真的會寫到腳本，也是這樣。卡片上會寫：
    「smurg 會先問，是因為這個資料夾的 Claude Code 專案設定會執行腳本，而 smurg 無法確定這個指令不會動到它們。」
- **這項檢查看不到什麼，以及該怎麼做。** smurg 讀的是指令提到了什麼。完全沒提到這些腳本的程式（`npm run build` 這類建置、
  專案裡會改寫另一個腳本的腳本），在執行之前是看不到的。除非有人把它那一類設為一律允許，它會和其他指令一樣先問；smurg
  事後會發現腳本變了，停止那個資料夾的 agent 並再問你一次，但是在這中間觸發的 hook，會以你的身分把改過的腳本執行一次。
  另外，腳本自己再去執行的東西完全不會被追蹤：能編輯資料夾裡檔案的人，都能改變你確認過的指令最後會執行什麼。所以請把
  hook 要執行的腳本放在 `.claude/hooks/`（組員不能寫那裡，agent 也不會自己去寫），hook 裡也只寫那裡的檔案。hook 指令
  提到的每一個已經存在的檔案，都算是它的腳本（`tsc -p tsconfig.json` 會把 `tsconfig.json` 記下來），放這個檔案的資料夾
  也就變成 agent 的檔案指令要先問的地方。
- 你隨時可以在主人控制台的
  「Claude Code 專案設定」查看這些設定、改變你的決定；決定會在 session 的 agent 下次啟動時生效。`smurg status` 會顯示
  分享資料夾的狀態（§7）。

**`CLAUDE.md` 由你來改。** Claude Code 會把 `CLAUDE.md` 和 `CLAUDE.local.md` 當成指示來讀，而這裡的 agent 是以你的身分
執行的。透過 smurg 只有你能改這些檔案，不論它們在資料夾的哪一層；組員看得到（`CLAUDE.local.md` 除外）但不能改，組員開的
session 的 agent 也不能改。工作項目的變更如果動到這類檔案，smurg 絕不會自己合併它，也不會從它的報告提供合併：它會列出這些
檔案等你處理，你可以請它的 agent 拿掉這些變更，或自己提出合併請求，讀過 diff 之後再合併（§10.3）。專案設定的檢視不會顯示這些檔案：只要資料夾的設定在使用中，或資料夾根本沒有設定，agent 就會讀它們。從別的地方
拿來的儲存庫，分享之前請自己先讀過它的 `CLAUDE.md`。

### 5.4 存在你磁碟上的對話

- **位置**：`~/.smurg/workspaces/<工作區代碼>/transcripts/`，只有你的帳號讀得到，在分享的資料夾之外；組員的檔案請求
  碰不到它。每個成員都在網頁上讀這些對話（§4）。
- **保存的內容**：對話裡顯示過的東西：人傳的訊息、agent 寫的文字、它的工具做了什麼（指令和輸出、編輯和 diff）、選擇題
  與投票和留言、權限請求與回答、建議。**不保存**：agent 只是讀過的檔案內容、它搜尋到的那些行，以及它的思考過程。
- **保存多久**：主題的對話和主題一樣久，不論有沒有封存；在網頁上刪除已封存的主題，就會刪除它的對話。不屬於主題的
  agent session，對話在 session 結束 30 天後移除。單一段對話最多保存 256 MB，超過之後最早的部分會被移除
  （「這段對話最早的部分已不再保留。」）。一個工作區的所有對話加起來超過 2 GB 時，最早結束、不屬於主題的 session
  先被移除；之後不會再默默移除任何東西：你會在收件夾收到
  「對話紀錄佔用的磁碟空間超過上限」，再自己刪除已封存的主題。
- **移除單一內容**：身為主人，你可以移除對話裡的某一則內容（那一則上的「移除這則內容…」），例如印出機密的指令輸出。
  人傳的訊息、smurg 自己的訊息、agent 寫的文字和它的工具各行，都有這個功能。那一則會從磁碟上刪除，所有人在原來的位置
  看到「主人已移除這則內容」。
- **移除一則內容，不會移除什麼**：已經看過的人不會因此沒看過；Claude Code 自己的對話紀錄（見下面）裡還有它；smurg 存在
  對話以外的副本也還在。選擇題（連同投票和留言）、權限請求（連同它顯示過的指令或 diff）和建議都是卡片：對話裡只有指向
  它們的位置，卡片本身不會變。收件夾項目裡的摘錄、結果報告下面追問的問題，以及操作紀錄，也都還在。刪除主題會把這些全部
  移除，只有操作紀錄除外。不屬於主題的 session 沒有這個辦法：它的對話要等 session 結束 30 天後才會移除。請你確認移除的
  對話框會寫出這一則屬於哪一種情況。
- **Claude Code 自己的紀錄**：Claude Code 在 `~/.claude/` 裡保存它自己的對話紀錄，依它自己的期限（預設 30 天）；smurg
  不會讀取也不會刪除它。那是 agent 的記憶。Claude Code 把它移除之後才繼續的 agent，對話裡會顯示
  「Claude Code 已不再保留先前的對話，Claude 會從檔案重新開始」
- `smurg uninstall` 會連同 `~/.smurg` 的其他內容一起移除對話（§9.5）。
- **操作紀錄**在同一個工作區資料夾裡（`audit.jsonl`，最多三個檔案、每個 32 MB；最舊的紀錄先被移除），它保存傳給 agent
  的完整文字。為了不讓某位成員的迴圈把其他紀錄全部擠掉，同一位成員被接受的同一種請求，每分鐘最多記 120 筆。那一分鐘
  其餘的請求會完整寫進紀錄旁邊的 `audit-overflow.jsonl`，紀錄裡則多一筆說明有幾筆。主人控制台只讀操作紀錄：要查這種
  大量的請求時，請自己打開那個檔案（一行一筆，格式相同）。不會被移到那裡的：你自己在網頁上做的事、agent 做的事，以及
  每一次改角色、移出成員、對專案設定的決定和移除內容。

### 5.5 agent 的 shell 指令通知

預設開啟；關掉：`--no-bash-attribution`。這項設定只能在啟動時決定：要改就先停止分享，再用新的選項執行 `smurg host`
（同一個資料夾的工作區和成員都會保留，組員不用重新加入）。分享中目前是開啟還是關閉，用 `smurg status` 查看（§7）。

agent 用 Edit、Write 等工具改檔案時，smurg 本來就知道是哪個 agent 改的。agent 用 shell 指令（例如 `sed -i`、
格式化工具）改的檔案，smurg 原本只能在活動動態裡顯示成「外部程式」。現在：

- 每個 agent session 執行 shell 指令時，會通知這台電腦上的 smurg 指令何時開始、何時結束。這個通知不會擋下任何指令：
  smurg 沒有回應時，只是不會記在那個 agent 名下。（指令到底能不能執行，在這之前就決定了，見 §5.2。）
- 檔案在「只有一個 agent 正在執行 shell 指令」的期間（加上指令結束後 3 秒）被改動，而且沒有其他人認領，就記成
  那個 agent 改的，例如「Claude (Amy) 透過 shell 指令修改了 src/app.ts」，操作紀錄也一樣。同時有兩個以上的 agent
  在執行 shell 指令時，仍然顯示「外部程式」。
- 已知限制：agent 執行 shell 指令的期間，你用 smurg 以外的工具（別的編輯器、自己的終端機）改了同一個範圍裡的檔案，
  也會被記成那個 agent 改的。
- 代價：每個 shell 指令多執行兩次小程式，在開發用的電腦上量到每次約 0.05 秒。

關掉之後，agent 用 shell 指令改的檔案在活動動態裡顯示為「外部程式」。檔案鎖與衝突處理不受這項設定影響。

## 6. 防止睡眠

分享期間 smurg 會防止電腦**閒置時**進入睡眠（macOS：`caffeinate`；Linux：`systemd-inhibit`）。
**闔上筆電螢幕仍然會睡眠**，這時組員會看到「主人已離線」。無法防止睡眠（例如 Linux 找不到 `systemd-inhibit`）或
之後失效時，`smurg host` 會在終端機提示一行；用 `--no-keep-awake` 關掉時不提示。目前的狀態用 `smurg status` 查看
（「防止睡眠：」那一行）。

在 Ubuntu 上透過 SSH 啟動 `smurg host` 時，系統（polkit）預設不允許防止睡眠，`smurg host` 會提示「⚠ 防止睡眠：未啟用
（系統（polkit）不允許防止睡眠…）」（在 Ubuntu 24.04 上驗證過；其他發行版或公司自訂的 polkit 規則也可能拒絕，訊息相同）。要防止睡眠，請在這台電腦的桌面登入後啟動 `smurg host`；沒有桌面的伺服器通常本來就
不會自動睡眠。

## 7. 狀態與停止

```sh
smurg status          # 這台電腦上正在分享的工作區（見下面）
smurg stop            # 停止分享：中斷所有連線、結束終端機 session、暫停 agent session
```

`smurg status` 列出每個正在分享的工作區（`smurg host` 啟動時不印的資訊都在這裡）：

- 工作區代碼、分享的資料夾、relay 的網址（公用 relay 會註明）與連線狀態、連線數與線上成員；
- **daemon 金鑰指紋**（§3）；
- 防止睡眠（§6）；
- agent 的 shell 指令通知（開啟／已關閉，§5.5）；
- 「Claude Code：」：它的版本、這個 smurg 有沒有驗證過這個版本或是版本太舊不能執行 agent session，以及有沒有登入
  （還沒檢查之前是「尚未檢查（第一個 agent session 啟動時 smurg 會檢查）」）；
- 「agent session：」：有幾個執行中、在等人回應、沒寫報告就停下或失敗、待命；
- 「主題：」：有幾個，其中幾個在執行、在等決定、待驗收或已暫停，例如「3 個（1 個執行中、1 個在等決定、1 個待驗收）」
  （§10.3、§10.5）；
- 「Claude Code 專案設定：」：「已確認（agent 會使用）」、「尚未確認（agent 不會載入；請在網頁上確認）」或「這個資料夾沒有」（§5.3）；
- 「你自己的 Claude Code 允許規則：」：有幾條套用到 agent session（§5.3）；
- daemon 紀錄檔的位置：`~/.smurg/logs/<工作區代碼>.log`（權限 0600，不含邀請連結）。出問題時，詳細原因在這裡。

在 `smurg host` 的終端機按 Ctrl-C 和 `smurg stop` 一樣（停止需要幾秒鐘；2 秒內再按一次不會中斷它，之後再按一次會立即
結束，但可能沒有完整停止）。

**停止對 session 的影響。** 終端機 session 會結束。agent session 會暫停：agent 停止執行，它的指令啟動後還留著在跑的程式
（開發伺服器、監看檔案的程式）也會一起結束，對話會保留，smurg 會說有幾個，
例如 `3 個 agent session 已暫停，下次分享這個資料夾時會繼續。` 它也會說下次啟動時有幾個主題會自己繼續；要讓其中一個
保持停下，請在停止 `smurg host` 之前，先在它的計畫裡按「暫停」（§10.5）。再次分享這個資料夾時，每一段對話都讀得到，計畫會在 `smurg host` 說明是哪些
之後自己繼續：被中斷的工作項目會被告知繼續，在等待的會在可以開始時開始。有人暫停的計畫會一直暫停，直到你或「可使用 agent」
的成員按「全部繼續」；有工作項目直接在分享的資料夾裡執行的計畫也一樣（§10.5）。討論和不屬於主題的 session 則在下一則訊息
來時繼續。還在等 agent 讀的訊息會保留下來，等那個 session 下次啟動時依序送出。工作到一半的 agent 會這樣顯示：
「主人電腦上的 smurg 重新啟動了，agent 的這一輪被中斷」

如果 `smurg host` 沒有正常停止就結束了（當掉、被強制結束、電腦斷電），agent 自己的程序可能還會多活一下子。它們什麼都
做不了：agent 每一次使用工具都要先問 smurg，smurg 不在時一律被拒絕。在這一輪結束之前，agent 仍然可能從模型收到一些
文字，這會算在你帳號的用量上。下次啟動之後，smurg 會結束剩下的程序，對話裡會顯示
「smurg 在這個 agent 工作時停止了。agent 可能自己又繼續了一會兒，請檢查它的變更。」

分享期間 `smurg host` 會在終端機告訴你：與 relay 的連線中斷與恢復、relay 拒絕了你的登入（登入過期，組員無法連線）、
登入快要到期（24 小時內）、smurg 的狀態檔寫不進磁碟，以及儲存庫在追蹤 smurg 自己的 `.smurg` 資料夾（只說一次，
§10.2）。登入過期或快到期時，在**另一個終端機**執行
`smurg login`（用同一個帳號；分享用的 relay 不是你最後一次登入的那個時，加上 `--relay <那個網址>`），`smurg host` 會在
幾秒內自動改用新的登入，不必重新分享。

你自己要在終端機裡接上終端機 session：`smurg attach`（先列出終端機 session，再列出 agent session 和它們的主題與狀態）、
`smurg attach <編號>`，按 Ctrl-] 離開。agent session 是對話：要在瀏覽器裡開啟，不是在終端機裡。

|---|---|

| 兩個連結上面：「這個工作區之前的狀態資料夾還放在旁邊」 | 你（或更新後照 smurg 0.5.0 的指示）之前把這個工作區的狀態資料夾移走了，現在使用的是新的工作區。§9.4 說明怎麼換回舊的，以及什麼時候不該換。這一行只印一次。 |
| 兩個連結上面：一則警告，說較舊的檔案「被放回這個工作區，並且重新升級了」 | 有人把 smurg 在升級前保留的副本放回去，取代了正在使用的檔案。副本建立之後決定的每一件事都被取消了（§9.2）：請現在就到主人控制台把成員、角色和邀請連結看過一遍。 |
| 兩個連結下面：「有組員的網頁或 smurg 比這個 smurg 新，連線被拒絕了。請停止分享，執行 smurg update，再重新分享。」 | 有組員用比你新的網頁版（relay 已經更新）或比你新的 `smurg` 來連線，兩邊使用的通訊協定版本不同。在你更新之前，用較新版本的人都連不上。照這一行說的做（§9.1）。每次執行只印一次，而且只針對工作區認得的組員。 |
| 兩個連結下面：「有組員的網頁或 smurg 比這個 smurg 舊，連線被拒絕了。請那位組員重新整理網頁或更新 smurg；如果你用的是自己架的 relay，請重新部署它。」 | 組員還開著更新之前的分頁，或他電腦上的 `smurg` 比較舊；也可能是你分享用的 relay 提供的網頁版比較舊。請組員重新整理網頁或執行 `smurg update`；你自己的 relay 則要重新部署（§2.2）。 |
| 組員看到「主人的 smurg 比這個網頁舊」 | relay 提供的網頁版比你的 `smurg` 新，兩邊無法溝通。停止分享，執行 `smurg update`，再重新分享（§9.1）。 |
| `smurg status` 顯示「正由另一個版本的 smurg host 分享」，或 `smurg host`、`smurg update`、`smurg uninstall`、`smurg attach` 說有另一個版本的 smurg host 正在分享 | `smurg` 指令被換掉了，但較早版本的 `smurg host` 還在執行（例如在分享中重新安裝），兩者無法溝通。停止正在執行的那一個（`smurg stop` 可以跨版本使用，或到它的終端機按 Ctrl-C），再用 `smurg host` 重新啟動。這種情況下 `smurg status` 的結束代碼是 5（0：有顯示分享中的工作區；3：沒有分享任何工作區）。已知的限制：如果還在執行的是 0.4.0 的 `smurg host`，`smurg status` 會照常顯示，結束代碼是 0，因為 0.4.0 的回覆裡沒有版本；`smurg attach` 則會說有另一個版本正在分享。 |
| 組員的網頁（或你自己的）顯示「安全警告：已拒絕連線」，或是打開連結時被問「主人的電腦金鑰和之前不同」 | 那個瀏覽器或那台電腦記下的 daemon 金鑰，和 `smurg host` 現在用的不一樣：你換過工作區的金鑰（§5.1「收回之後」第 1 步，或 §9.3 最後的辦法），或是換回了之前移走的狀態資料夾（§9.4 說明哪些人會遇到）。看到警告的人只能靠連結繼續：你自己打開「你的連結」，給組員新的邀請連結，並用其他管道（當面、電話）把 `smurg status` 顯示的 daemon 金鑰指紋告訴他，讓他在連結問到金鑰換了的時候可以比對。這些你都沒做過的話，請他不要繼續：可能有人冒充你。 |
| 「smurg 的狀態目錄路徑太長」 | 把 `SMURG_HOME` 設成較短的路徑（Unix socket 路徑有長度上限）。 |
| 組員看到「主人已離線」 | `smurg host` 沒有在執行，或電腦在睡眠 / 沒有網路。 |
| 主題或 agent session 開不起來：「主人電腦上的 Claude Code 尚未登入，無法啟動 agent session。主人需要執行 `claude` 並登入」（已經開著的 session 顯示「主人電腦上的 Claude Code 尚未登入。」） | 每個 agent 都用你在這台電腦上的 Claude Code 登入（§5.1）。在你自己的終端機執行 `claude` 並登入；session 裡沒有辦法登入。然後在 session 裡按「重新檢查登入」，或直接傳下一則訊息。 |
| 「Anthropic 拒絕了主人的 Claude Code 登入，主人需要在自己的終端機重新登入。」 | 這台電腦上的登入已經不被接受。在你自己的終端機執行 `claude`，登出再重新登入。 |
| agent session 開不起來，訊息的最後是「請主人更新 Claude Code」 | agent session 需要 Claude Code 2.1.288 以上（§1）；訊息裡會寫它找到的版本。請更新 Claude Code（`claude update`，或用你當初安裝的方式）。`smurg status` 會顯示 smurg 看到的版本。 |
| 「找不到 claude 指令」／「session 啟動時 Claude Code 沒有回應。請主人在自己電腦的終端機確認 `claude` 可以執行。」 | 你的帳號沒有安裝 Claude Code、它不在啟動 `smurg host` 時的 `PATH` 裡，或是它啟動不了。請在你啟動 `smurg host` 的那個終端機執行 `claude` 試試。失敗的 session 有「再試一次」；連續三次啟動失敗之後，只有你可以再試。 |
| 「主人的 Claude 帳號已達用量上限。」（你的收件夾：「主人的 Claude 帳號達到用量上限」） | `claude` 登入的帳號目前沒有可用的用量。每個 agent 都會等待；Claude Code 有回報時間的話，網頁上會顯示額度什麼時候重置。帳號可以用了之後，smurg 會請每個因為用量限制停下來的工作項目繼續（「主人的用量限制已經重置：smurg 請 Claude 繼續」；這一點沒有用真正的帳號試過）；其他 session 則在下一則訊息來時繼續。很多 agent 同時工作會很快用完訂閱的額度（§10.4）。 |
| 工作項目顯示「沒寫報告就停下了」或「被人停止，沒有報告」 | 它的 agent 沒有寫結果報告就結束了這一輪，即使 smurg 又請過它一次（「smurg 請 Claude 寫結果報告」）；或是它還沒寫報告，就有人把它停止了。打開 session 看它做到哪裡；「繼續」會請 agent 接著做。 |
| 工作項目顯示「因錯誤停止，沒有報告」，它的對話裡顯示「smurg 讀不到這個項目的變更，所以報告還沒有登記。agent 的下一回合結束時會再試一次」 | agent 寫了報告，但 smurg 沒辦法把這個項目的變更和報告一起記下來：有人一直在 worktree 裡打字、裡面還有另一個 git 儲存庫，或 git 花了太久。記得下來之前，不會有報告出現。smurg 會在一分鐘後自己讓工作項目的 agent 繼續一次（「smurg 沒能記下這個工作項目的變更：它請 Claude 繼續，那一輪結束後再記一次」）；否則「繼續」會讓它接著做。它的下一輪結束時，報告就會登記。之後的報告版本如果也記不下來，原來的版本會維持不變，對話裡顯示同一句話。 |
| agent session 開不起來：「這個 session 的資料夾路徑含有反斜線或控制字元，Claude Code 的權限規則無法表示這樣的資料夾，所以無法在這裡啟動 agent session。請主人重新命名資料夾」 | 把分享的資料夾（或路徑上有那個字元的上層資料夾）重新命名，再重新分享。這樣的資料夾裡檔案和終端機都能用，只有 agent session 會被拒絕。路徑裡有空白、括號、中括號和其他符號都沒有問題。 |
| 工作項目顯示「失敗」（你的收件夾：「agent 的程序失敗了」），或它的 session 顯示「agent 的程序意外結束」 | Claude Code 的程序結束了。smurg 會在一分鐘後自己重新啟動工作項目的 agent 一次（「Claude 的程序停止了：smurg 重新啟動它一次，並請它繼續」）；之後「再試一次」會接續同一段對話。一直失敗的話，看 daemon 的紀錄檔（§7）。 |
| 工作項目顯示「計畫有變動：請重新開始」（你的收件夾：「沒有開始」）：「spec 或計畫在開始之後有變動，這個項目沒有開始」 | 工作項目只會從有人按下開始時確認過的 spec 和計畫開始（§10.2）。打開計畫，看看改了什麼，再按這個項目上的「重新開始」。 |
| 工作項目沒有開始：「從按下開始到現在，smurg 保存這個資料夾版本紀錄的方式變了。請看過計畫，再重新開始這個項目。」 | 它的開始選定的版本紀錄現在不能用了：git 不見了或不能執行、資料夾的 `.git` 不見了或出現了，或 smurg 自己的版本紀錄被拒絕了（見下面幾列）。項目只會在它自己的開始選定的版本紀錄裡執行，絕不會自己換到另一個，也絕不會自己直接在資料夾裡執行。把變了的地方處理好，再按「重新開始」（§10.2）。 |
| 工作項目顯示「沒有合併：沒有完成（部分完成）」、「沒有合併：沒有完成（受阻）」或「沒有合併：報告無法讀取」（決定的人的收件夾：「… 沒有合併：…」） | 它的報告說工作沒有做完，或 smurg 請 agent 修正之後仍然讀不了報告：smurg 只合併報告寫著完成且驗證過的項目（§10.3）。項目的負責人有「可使用 agent」時由他決定，否則由你和「可使用 agent」的成員決定；過了等待時間（§10.6）之後你們都可以決定。在報告下面寫要改什麼（「請 agent 修正」），或「略過這個項目…」；你也可以用「合併…」讀過 diff，就這樣合併。只有這個項目和依賴它的項目會等。沒有 git 時（§10.2），這樣的項目會讓依賴它的項目不能開始，你也可以按「就這樣接受」。 |
| 「沒有合併：有驗證失敗」或「沒有合併：沒有通過的驗證」 | 報告列出了一項失敗的驗證，或沒有任何一項通過。可以做的事和上一列一樣：通常是追問，請 agent 讓驗證通過，並在報告裡寫出來。 |
| 「沒有合併：沒辦法順利合併」 | 這個項目的變更和它開始之後其他工作項目合併進來的東西有衝突，它的 agent 試了三次都沒有解決（§10.3）。「請 agent 解決衝突」會再試一次（不算在次數裡）、「合併…」可以看衝突，或「略過這個項目…」。 |
| 「沒有合併：和 Amy 對 src/app.ts 的修改衝突」或「沒有合併：和在 smurg 以外對 src/app.ts 的修改衝突」 | 衝突的另一邊是某個人的修改（你的、組員的，或在 smurg 以外做的提交），不是工作項目的。smurg 絕不會讓 agent 自己蓋過人寫的內容：項目的底部會列出每個檔案和是誰改的，要留下誰的內容由人決定。「請 agent 解決衝突」（它收到的訊息會說哪些檔案裡有人的修改，而且要留著）、讀過 diff 之後自己合併，或「略過這個項目…」。 |
| 「沒有合併：Amy 在報告之後對 agent 說了話」、「沒有合併：它的上一輪沒有做完」或「沒有合併：最後一次修改之後沒有再檢查報告」 | 有人在報告之後對這個項目的 agent 說了話，但沒有新的版本；之後的一輪被停止了（或因錯誤結束，而 smurg 已經不再自己讓它繼續，§10.5）；或 agent 改了檔案之後沒有再檢查報告，smurg 也請過它一次。這個版本要有人說可以才會合併：「就這樣合併」（「可使用 agent」）、追問、沒做完的那一輪按「繼續」，或「略過這個項目…」。 |
| 「已合併；之後的變更沒有合併：它的 worktree 裡有從沒合併過的變更」或「已合併；之後的變更沒有合併：它的上一輪沒有做完」 | 這個項目已經合併了，它的 worktree 裡卻有任何一次合併都沒帶走的後來的變更：有成員在那裡存了檔、它的 agent 在報告之後用指令改了檔案，或之後的一輪被停止、或被重新啟動打斷。也可能是有一則傳給它的 agent、因為重新啟動而還沒送出的訊息在等（報告下方會這樣說，§10.5）。已經合併的版本會留在資料夾裡。由它的負責人決定（負責人有「可使用 agent」時，否則由你和「可使用 agent」的成員）：「繼續」讓它的 agent 把這個變更做成新的版本，它會和第一次一樣合併。在那之前，主題不會待驗收。 |
| 「沒有合併：主人沒有合併它」 | 你拒絕了它的合併請求。在報告下面追問，或「略過這個項目…」。 |
| 「沒有合併：改到只有主人能合併的檔案」 | 它的變更動到只有你能改的檔案（§5.3）、主題自己的 `SPEC.md` 或 `PLAN.md`、指向專案以外的連結，或 smurg 的 `.smurg`；項目的底部會列出它們。只有你能決定：「請 agent 拿掉它們」（它會復原對這些檔案的修改，保留其他的）、在項目上「請求合併」並讀過 diff 之後合併，或「略過這個項目…」。 |
| 「沒有合併：Amy 手動改了它的檔案」 | 沒有「可使用 agent」的成員（「可編輯」）改了項目 worktree 裡的檔案：smurg 不會不經人讀過就合併這種修改。有「可使用 agent」的成員本來就能讓 agent 做同樣的修改，所以他們改的會和 agent 的一起合併。用「合併…」讀過 diff 再合併，或「略過這個項目…」。 |
| 「沒有合併：主工作區有還沒提交的修改擋住了」 | 在資料夾自己的 git 裡，合併要動到的某個檔案有還沒提交的修改（可能是組員的），smurg 絕不會覆蓋它們。把它們提交或復原：完成之後 smurg 會自己合併這個項目（那些檔案有變動時它會再看一次，最晚每分鐘一次）。 |
| 「沒有合併：主工作區有檔案擋住了」 | 項目要新增檔案的位置上，有 git 沒有追蹤的檔案。把它們移走（smurg 絕不會覆蓋它們），或略過這個項目；移走之後 smurg 會自己合併它。 |
| 「沒有合併：主工作區有已暫存的變更」 | 主工作區裡有已暫存的東西（`git add`），git 不會在它上面合併。把它提交或取消暫存；之後 smurg 會自己合併這個項目。你自己合併時會看到「主工作區有已暫存的變更（git add），git 不會在它們上面合併。請先提交或取消暫存，再合併。」 |

| 「沒有合併：主工作區的 git 已經忙了一段時間」，或工作項目顯示「等著合併：主工作區的 git 正在忙」 | 主工作區正在進行合併、rebase 或類似的 git 操作（第一種情況是已經十分鐘了）。把它做完或中止；之後 smurg 會自己合併。如果那是 smurg 停下來時正在做的合併（它的訊息最後一行是 `Merged-by: smurg (automatic merging, the host's setting)`），請用 `git commit` 完成它，或執行 `git merge --abort`。 |
| 「沒有合併：主工作區有一次復原被中斷了」 | smurg 在一次復原的途中停下來了（§10.3），主工作區停在中間。用 `git restore --staged --worktree -- <paths>` 把檔案還原（`git status` 會列出它們）。之後 smurg 會自己繼續；在那之前，什麼都不會自己合併或復原。 |
| 「沒有合併：smurg 為資料夾保存的版本紀錄變了」或「沒有合併：smurg 沒辦法合併它」 | smurg 自己的版本紀錄被 smurg 以外的程式改了（下面幾列說明怎麼處理），或 `git merge` 因為別的原因失敗了兩次。「合併…」會說明錯誤；或「略過這個項目…」。 |
| 工作項目顯示「等著合併：Amy 正在編輯」 | 有人正在這個項目改到的某個檔案裡打字。他停下來之後，項目會自己合併。 |

| 組員的開始對話框顯示「沒有 git 時，只有主人能讓工作項目開始：它們會直接在分享的資料夾裡執行。」 | 沒有 git 時，只有你能讓工作項目開始或再試一次（§10.2）。請自己開始它們，或照上面幾列安裝 git。 |

## 9. 更新與移除

### 9.1 更新：`smurg update`

```sh
smurg update --check    # 只檢查有沒有新版本，不下載
smurg update            # 更新到最新版本
```

- `smurg update` 先讀 `https://downloads.smurg.ai/latest/VERSION`。有比目前新的版本時，從
  `https://downloads.smurg.ai/v<版本>/` 下載這台電腦的執行檔和那個版本的 `SHA256SUMS`，**sha256 相符**、檔案確實是那個
  版本、而且在這台電腦上能執行，才把目前的執行檔原地換掉，然後印出舊版本、新版本和變更紀錄的網址
  （https://smurg.ai/zh-TW/docs/changelog/）。已經是最新版本時什麼都不做，也不會換成較舊的版本。
- **正在分享時不能更新**：`smurg update` 會請你先執行 `smurg stop`，它不會自己停止分享。原因：還在執行的 daemon 是舊版，
  而 agent session 每次呼叫的 `smurg` 指令已經是新版，兩個版本混在一起可能出錯。
- **你的工作區會保留下來。** 新版本第一次執行 `smurg host` 時，會讀取舊版本寫的內容（成員、邀請連結、金鑰、設定、主題、
  對話）並沿用；不會重設任何東西，也沒有人需要重新加入（§9.2）。每個版本改了什麼，寫在變更紀錄裡。
- **你的 `smurg`、網頁版和每位組員的 `smurg attach` 必須使用同一個通訊協定版本。** 網頁版來自 relay，公用 relay 會在每個
  新版本發佈時更新。網頁比你的 `smurg` 新的期間，組員會看到「主人的 smurg 比這個網頁舊」，要等你更新之後才連得上；
  `smurg host` 拒絕這樣的組員時，會用一行告訴你（§8）。分頁或 `smurg` 比較舊的組員，則會被告知要重新整理或更新。你用
  自己架的 relay 時，每次更新都要重新部署它（§2.2）。
- **不支援換回較舊的版本。** `smurg update` 絕對不會安裝較舊的版本。較新版的 smurg 分享過的工作區，較舊的版本可能拒絕：
  smurg 0.4.0 會拒絕 0.5.0 以上分享過的每一個工作區，0.5.0 會拒絕 0.6.0 以上分享過的每一個工作區，而它們的訊息會要你把
  工作區的資料夾移走。不要照做（照做過的人請看 §9.4）：請重新安裝最新版本。（0.5.1 和 0.5.2 會說什麼都沒有改，要你執行
  `smurg update`。）
- 下載失敗、sha256 不符，或你按了 Ctrl-C：目前的執行檔不會被更動，下載到一半的暫存檔會刪除。
- 執行檔所在的資料夾不能寫入時（例如不是用安裝程式裝的），它會說是哪個資料夾：請用當初安裝的方式更新，或重新執行 §1 的
  安裝指令。
- 信任的範圍和安裝程式相同：`SHA256SUMS` 沒有數位簽章，靠的是 https 和 downloads.smurg.ai 本身。
- 環境變數 `SMURG_INSTALL_BASE_URL`（測試或鏡像站用）：改從這個網址下載。只接受 https。

**新版本提示**：`smurg host` 印出兩個連結之後，會在背景向 `https://downloads.smurg.ai` 查一次最新版本（只有這一個請求，
不附帶任何資料，最多等 2 秒）。有新版本時，在連結下面多印一行：

```text
有新版本 0.5.1（目前 0.5.0）：停止分享後執行 smurg update
```

沒有新版本、查不到或逾時時什麼都不印，也不影響分享。不要這個檢查：設定環境變數 `SMURG_NO_UPDATE_CHECK=1`。自動化環境
（設定了 `CI`，或不是在終端機裡執行）不會檢查。

### 9.2 更新之後：工作區保留了什麼

`smurg update` 只換掉執行檔，不動其他東西。工作區自己的狀態（`~/.smurg/workspaces/<工作區代碼>/` 這個資料夾：daemon 金鑰、
成員、邀請連結、設定、主題、對話、操作紀錄）要等你下一次分享那個資料夾時才會被讀取，`smurg host` 分兩步做：

1. 先**讀取**工作區狀態的每一個檔案，什麼都不改。較早發佈的版本（0.4.0 和之後的每一版）寫的內容，會在記憶體裡轉成
   現在的格式。只要有一個檔案不能用，`smurg host` 就不啟動，工作區和原來一模一樣（§9.3）。
2. 全部都讀得了，才開始**寫入**：先寫一個小檔案，記下是哪個版本的 smurg 在分享這個工作區（`written-by.json`）；再對每個
   轉成新格式的檔案，先留一份原本的副本（見下面），然後寫入新格式的檔案。這一步如果中途被打斷（磁碟滿了、停電），不會
   遺失任何東西：檔案要先留好副本才會被換掉，下一次執行 `smurg host` 會把剩下的做完。

第 2 步有檔案寫成新格式時，兩個連結上面會多一行說明，只在那一次啟動時印出：

```text
這個工作區上次是用 smurg 0.4.0 分享的：成員、邀請連結和設定都已沿用。有哪些改變：https://smurg.ai/zh-TW/docs/hosting/#92-更新之後工作區保留了什麼
```

**從 0.4.0 原樣沿用的：**

- 工作區本身：同一個工作區代碼、同一把 daemon 金鑰。金鑰指紋就是組員核對過的那一組，不會有人被問金鑰是不是換了；
- 每位成員和他的角色、每個裝置：組員不需要新的邀請連結就能再打開工作區（瀏覽器重新載入網頁之後；用 `smurg attach` 的
  組員執行過 `smurg update` 之後）。被你移出的人還是被移出，被撤銷的裝置還是被撤銷；
- 邀請連結：還有次數的連結照樣能用，用完、被撤銷或過期的連結照樣被拒絕。和每次啟動一樣，上一次的主人連結會失效，
  並印出一個新的；
- 你在主人控制台改過的設定；
- 保留的 worktree 和裡面的工作、等你處理的合併請求、保留的衝突副本、中斷的上傳（從停下來的地方繼續）、已經決定的
  建議、操作紀錄和活動動態；
- 這台電腦上的：你的 relay 登入，以及哪個資料夾對應哪個工作區的紀錄。

**0.4.0 之後才有的設定，更新後是這些值**（在主人控制台的設定裡可以改）：

- 「agent 可以使用我自己的和這個專案的 MCP 伺服器」：關閉（§5.3）。更新絕對不會把它打開；
- 選擇題或權限請求等多久之後會轉給其他人：5 分鐘（§10.6）；
- 「同時執行的工作項目數量」：和這台電腦上新建的工作區一樣（§10.4）。

**沒有跟過來的，以及原因：**

- session。在 0.4.0，沒有任何 session 能在 `smurg stop` 之後留下來：終端機已經結束，它的 agent session 也是終端機，
  所以沒有對話可以接著進行。
- 停止分享時還在等回覆的建議：會被關閉，0.4.0 自己每次停止時也是這樣處理。
- 用較舊的 Claude Code 開 agent session：現在需要 2.1.288 以上（§1）。
- 組員的 `smurg` 0.4.0，以及更新之前就開著的瀏覽器分頁：兩者都會被拒絕連線，直到組員更新或重新整理（組員指南的
  §8 和 §10）。

**0.4.0 留下的角色和邀請連結，現在能做的事變多了。** 角色的名稱沒有變，每位成員、每個還沒用過的邀請連結也都保有原來的
角色。但是 0.5.0 讓這些角色能做更多事，而你的工作區並沒有人重新決定過：

- **可編輯**現在也能參與主題：對 agent 的選擇題投票、留言，並檢視結果報告。
- **可使用 agent** 現在也能建立主題並開始其中的工作項目、傳訊息給 agent、回答 agent 要在你電腦上執行什麼的請求，
  以及更換 session 的負責人。
- **旁觀**和以前一樣，只能看。

在 0.4.0 建立、還沒用過的連結，誰打開它，誰就得到那個角色現在的權限。更新之後，請到主人控制台把成員和邀請連結看過
一遍：今天不會給的角色就改掉，不會給的連結就撤銷（§5.1 說明「可使用 agent」代表什麼）。

**更新到 0.6.0：agent 以自動模式執行。** 這次更新特意把一項設定往和之前每一次更新相反的方向改：工作區的模式變成
「自動：檢查通過就執行」（§5.2），從 0.4.0 和從 0.5.x 更新都一樣。在 0.5.x，agent 幾乎每個指令執行之前都會先問；現在由
Claude Code 的檢查決定哪些指令不用問任何人就執行。`smurg host` 會在上面那一行下面說明一次：

```text
agent 現在以自動模式執行：由 Claude Code 的檢查決定哪些指令不必先問就執行；agent 在自己資料夾裡改檔案和簡單的檔案指令，不經過這道檢查。想要執行指令前再先問，請在主人控制台的設定裡選「執行指令前先問」。說明：https://smurg.ai/zh-TW/docs/hosting/#52-agent-自己能做什麼什麼要先問
```

你的收件夾會有「agent 現在以自動模式執行」，主人控制台的設定裡也會一直顯示同樣的說明，直到你按「知道了」。想要再被
問，請在那裡的「agent 不必先問就能做的事」選「執行指令前先問」（或「編輯和執行指令前都先問」）。這次更新之後還有：

- 有人改得更嚴格的 session（工作項目，或在 worktree 裡的 session，選了「編輯和執行指令前都先問」）會保留那個選擇；其他
  每個 session 都跟隨工作區的模式；
- 每個 session 都和以前一樣用主人的預設模型：還沒有人選過模型（§5.1）；
- 上面那一行會寫出上一次分享這個工作區的 smurg（例如「這個工作區上次是用 smurg 0.5.2 分享的」）。

**更新到 0.7.0：工作項目會自動合併。** 這次更新也特意把一項設定往相反的方向改：「合併工作項目」變成
「報告寫著完成且驗證過的，由 smurg 合併」（§10.3），從之前每一個版本更新都一樣。在這之前，每個工作項目都要等你讀過 diff
再合併；現在工作項目的報告寫著完成、至少一項驗證通過、沒有驗證失敗，而且能順利合併時，smurg 會替你把它合併到分享的
資料夾。`smurg host` 會在上面那幾行下面說明一次：

```text
工作項目現在會自動合併：報告寫著完成、至少一項驗證通過、沒有驗證失敗時，smurg 會替你把它合併到分享的資料夾，主題待驗收時每個人的收件夾都會顯示。這次更新之前就開始的工作項目仍然會等你。想要每個項目都自己合併，請在主人控制台的設定裡選「每個項目都由我自己合併」。說明：https://smurg.ai/zh-TW/docs/hosting/#103-合併以及什麼在等它
```

你的收件夾會有「工作項目現在會自動合併」，主人控制台的設定裡也會一直顯示同樣的說明，直到你按「知道了」或在那裡選了設定。
想要每個項目都自己合併，請在「合併工作項目」選「每個項目都由我自己合併」。這次更新之後還有：

- 之前的開始已經開始的工作項目仍然會等你合併；從現在起開始的工作項目會自動合併；
- 操作紀錄裡會有一筆由這次更新改了設定的紀錄，每一次自動合併也會寫出這是你選的設定，還是更新設定的；
- 重新啟動之後計畫會自己繼續（§10.5）：之前的版本在重新啟動時暫停的計畫，會在 0.7.0 第一次啟動時繼續，除非它有直接在
  分享的資料夾裡執行、被中斷的工作項目。

**smurg 保留的副本。** 把檔案寫成新格式之前，smurg 會在旁邊留一份原本的檔案，檔名帶著改寫它的那一步：0.4.0 的工作區是
`state.json.before-upgrade-from-0.4.0`、`suggestions.json.before-upgrade-from-0.4.0`，0.5.0、0.5.1 或 0.5.2 的工作區是
`state.json.before-upgrade-from-0.5.0` 和 `agent-sessions.json.before-upgrade-from-0.5.0`（這三版寫的格式相同），0.6.0 的工作區是
`state.json.before-upgrade-from-0.6.0`。副本之後不會再寫入，
只有你能讀（權限 600；每次啟動都會檢查，和狀態檔一樣），smurg 也不會去讀它。如果之後又有一個舊格式、而且不是這份副本的檔案被升級（你回去用舊版
smurg 工作了一陣子，然後再更新一次），smurg 也會把那個檔案留下來，檔名相同，最後多加 `-2`（再來是 `-3`，依此類推）。它是留給你查看工作區當時內容用的。裡面有邀請連結的金鑰：請和狀態檔一樣
小心保管，不需要時就刪掉。

**不要把副本放回去取代正在使用的檔案。** `state.json` 記錄了誰被移出、哪個裝置被撤銷、哪個邀請連結用完或被撤銷，以及
誰是什麼角色。把副本放回去，更新之後的這些決定全部取消：之後被移出的人又是成員，已撤銷的裝置、已撤銷或已用完的邀請
連結又可以使用，角色的變更也消失了；之後才加入的人不再是成員，之後建立的邀請連結也不能用了。smurg 擋不住這件事，但會在下一次啟動時告訴你：原本那一行的位置會換成一則警告，
說較舊的檔案「被放回這個工作區，並且重新升級了」；這時請到主人控制台把成員、角色和邀請連結看過一遍。

### 9.3 `smurg host` 拒絕工作區的狀態時

`smurg host` 要能讀取工作區的全部狀態才會使用它。否則它不啟動，也不更動任何東西：成員、邀請連結、金鑰和設定都和原來
一樣，你可以重試任意多次。`smurg:` 之後的幾行會指出檔案（或工作區的資料夾）、說明原因，並告訴你怎麼處理；daemon
自己記下的那一行在紀錄檔裡（`~/.smurg/logs/`）。如果是啟動到一半、已經開始寫入之後才被拒絕（例如磁碟滿了），終端機不會說
「沒有更動任何東西。」，而是說工作區裡的東西沒有被更動或重設：已經寫好的部分會留著，下一次啟動會接著做完（§9.2）。絕對
不要為了繞過拒絕而把工作區的資料夾移走：那會放棄成員、邀請連結和 daemon 金鑰。終端機只會把它當作最後的辦法、先說完代價
才提；可以單獨移到旁邊的檔案，則完全不會提（見表格下面）。

| 終端機顯示 | 發生了什麼，怎麼處理 |
|---|---|
| 「這個工作區上次是用比這個 smurg（0.5.1）更新的版本分享的，這個 smurg 讀不了它寫的東西」（工作區有記錄時，會寫出那個較新的版本） | 有較新版的 smurg 分享過這個工作區。執行 `smurg update`，再執行一次 `smurg host`。如果 `smurg update` 說已經是最新版本，表示寫入這個資料夾的 smurg 是這台電腦用更新拿不到的版本（沒有發佈過的版本，或是從別台電腦複製來的資料夾）：請用寫入它的那個 smurg 來分享。終端機會指出記錄寫入版本的檔案 `written-by.json`。 |
| 「這個工作區有一個狀態檔，這台電腦的其他使用者也能存取（權限 644）」 | 這個檔案的權限讓這台電腦的其他帳號可以讀取或更動它，smurg 不使用這樣的檔案。執行終端機印出的那一行 `chmod 600 …`（它會列出每個這樣的檔案），再執行一次 `smurg host`。在這之前那些帳號讀得到這個檔案，而工作區的狀態裡有 daemon 金鑰和邀請連結的金鑰：如果你不信任他們，請換掉金鑰（§5.1「收回之後」第 1 步）。 |
| 「這個工作區有一個狀態檔屬於其他使用者，不是你的」 | 通常是曾經用 `sudo` 執行過 smurg。`chmod` 不會改變檔案的擁有者：請檔案的擁有者或這台電腦的管理員把它交還給你（`chown`），再執行一次 `smurg host`。 |
| 「這個工作區有一個狀態檔是符號連結（symlink），smurg 不會跟著狀態資料夾裡的連結走」，或「這個工作區的狀態檔該在的位置上，是一個資料夾」 | smurg 在那個位置只讀屬於你自己的一般檔案。把檔案本身放在那裡（權限 600），再執行一次 `smurg host`。 |
| 「這個工作區有一個狀態檔無法開啟或寫入（沒有權限，EACCES）」（或系統給的其他原因） | 系統不讓 smurg 開啟或寫入這個檔案：權限、磁碟滿了、磁碟故障。遇到這種情況，smurg 絕對不會另外建立新的工作區。把原因指出的問題處理好，再執行一次 `smurg host`。如果終端機指出的檔案根本不存在（這個版本第一次啟動時的 `written-by.json`），表示 smurg 沒辦法建立它：請檢查工作區資料夾本身的權限。 |
| 工作區資料夾裡的「狀態檔寫的是另一個工作區」 | 這個資料夾是從另一個工作區複製來的，或是兩個弄混了。沒有指令可以修好：請把這個工作區自己的資料夾放回原位。 |
| 「這個工作區的狀態檔不見了，可是工作區的其他檔案還在」，或「這個工作區的 daemon 金鑰不見了，可是它的狀態檔還在」 | 有檔案被手動移走、改名或刪除。smurg 不會另外建立新的檔案（新的狀態檔會忘記誰被移出，新的金鑰會讓每位組員的瀏覽器跳出警告）。請把檔案放回來。如果檔案真的找不回來，終端機會和檔案損毀時一樣往下列（見表格下面）：狀態檔的話，先是保留的最新副本（如果有），再來是最後的辦法；金鑰的話，只有最後的辦法。 |
| 「這個工作區有一個狀態檔已損毀：它不是有效的 JSON（可能是空的，或只寫了一半）」，或「這個工作區有一個狀態檔的格式，不是 smurg 0.5.1 或更早發佈的任何版本寫的」 | 檔案只寫了一半、被手動或其他程式改過，或是沒有發佈過的 smurg 寫的。「不符合的地方：」會列出檔案裡的位置和各自違反的規則（不會顯示檔案裡的值；規則的說明是英文，不論介面是哪種語言）。接著終端機會依序列出你能做的事（見表格下面）。 |
| 「較早版本的 smurg 寫的狀態檔裡，有一個值是 smurg 0.5.1 不接受的」 | 目前只知道一種情況：路徑或名稱裡有連續超過 30 個組合用符號，0.4.0 接受，之後的版本一律拒絕。「不符合的地方：」會指出是哪一筆（從 0 開始數），最後是 `mark-run`。它可能在 `conflicts.json`（保留的衝突裡的檔案）、`worktrees.json`（worktree 共用的資料夾、合併請求裡的檔案）或 `state.json`（`settings.sharedDirs`，也就是主人控制台的「共享資料夾（在 worktree 裡唯讀）」）裡。smurg 不會替你丟掉任何東西。前兩個檔案，終端機會提出把那一個檔案單獨移到旁邊（見表格下面）；`state.json` 則只會提最後的辦法。要保住工作區，可以自己把指出的那一筆從檔案裡拿掉（先留一份備份，權限維持 600），`smurg host` 就能啟動，其餘的內容照樣沿用。 |
| 「工作區紀錄檔（workspaces.json）是較新版的 smurg 寫的（這個 smurg 是 0.5.1）」（或 relay 的登入資料 `credentials.json`），或這兩個檔案之一「的格式不正確」 | `~/.smurg` 裡的這兩個檔案是這台電腦自己的：哪個資料夾對應哪個工作區，以及你的 relay 登入。smurg 不再把這樣的檔案當成空的再覆寫。是較新版的 smurg 寫的：執行 `smurg update`。格式不正確：把工作區紀錄檔修好，或把備份放回來（沒有它，`smurg host` 會幫資料夾建立新的工作區）；登入資料可以移走，再用 `smurg login` 重新登入。 |
| 「工作區紀錄檔（workspaces.json）裡，這個資料夾的那筆資料這個 smurg（0.5.1）讀不懂」 | 紀錄檔本身讀得了，但你要分享的這個資料夾的那一筆讀不懂；終端機會指出是第幾筆、哪些欄位讀不懂。`smurg host` 會停下來，因為少了這一筆，它會幫資料夾建立新的工作區。如果這台電腦用過較新版的 smurg，請執行 `smurg update`；否則請修好這一筆（格式見表格下面），或把檔案的備份放回來。smurg 讀不懂的資料絕對不會被丟掉：上面會有一則說明，寫出檔案裡有幾筆。 |

檔案損毀或格式不明時，終端機在「沒有更動任何東西。」之後會列出：

1. 「第一步：如果這台電腦曾經用過較新版的 smurg，請執行 smurg update，再執行一次 smurg host。」沒有任何紀錄說明資料夾是
   哪個 smurg 寫的時候才會出現：在較舊的 smurg 看來，較新版寫的檔案和損毀的檔案沒有兩樣。
2. smurg 在升級前為這個檔案保留的最新副本（§9.2），包括檔名和日期；在這之前會先說明把它放回去會取消什麼。對
   `state.json` 來說，就是副本建立之後決定的每一件事。只有在你要的正是工作區當時的內容時才用它，之後請把成員、角色和
   連結看過一遍。
3. 下面表格裡的檔案：「這一個檔案可以單獨移到旁邊，工作區不會因此不見：…」，接著說明這個檔案記了什麼，以及把這一個
   檔案移到旁邊、改名為 `<檔案>.set-aside-<日期>-<時間>` 的指令。成員、邀請連結、設定和 daemon 金鑰都會留著，下一次
   啟動時 smurg 會建立一個新的空檔案。這時不會印出最後的辦法。
4. 其他的檔案：「最後的辦法是建立新的工作區。」終端機會先說代價，才列出指令：這個工作區的成員和邀請連結、主題、對話和
   操作紀錄，還有 daemon 金鑰（組員要用新的連結重新加入，並且會被問金鑰是不是換了）；smurg 也不再認得它保留的
   worktree。它印出的指令會把資料夾移到一個帶有日期和時間的名稱，所以資料夾還留著，§9.4 的換回方法也還能用。

| 檔案 | 裡面記了什麼 | 移到旁邊只會失去這些 |
|---|---|---|
| `inbox.json` | 每位成員在收件夾裡看過、移除了什麼，以及為他們保留的提及 | 每個人收件夾裡的項目都變回還沒看過；保留的提及 |
| `suggestions.json` | 成員給 agent session 的建議 | 全部的建議；還在等的要重新提一次 |
| `conflicts.json` | 保留下來的衝突清單（成員和 agent 改到同一個檔案的地方） | 這份清單：不能再從 smurg 套用 agent 的版本。你的檔案不會被動到 |
| `worktrees.json` | smurg 建立的 worktree 和所有合併請求的紀錄，以及沒有 `.git` 的資料夾的 smurg 自己的版本紀錄 | smurg 不再認得任何 worktree（資料夾和裡面的工作還在 `.smurg/worktrees/`，要自己合併），還在等的合併請求也沒了。沒有 `.git` 的資料夾還要在下一次開始之前，把 `.smurg/git` 移出分享的資料夾：smurg 絕不會使用沒有紀錄的版本紀錄，下一次開始會建立新的（§10.2） |
| `sessions.json` | 有哪些終端機 session 正在執行 | 正常停止之後沒有影響；當機之後，那些終端機留下的程序 smurg 不會替你結束 |
| `host-rules.json` | smurg 上次看到的、你自己的 Claude Code 允許規則 | 沒有長久的影響：smurg 會再告訴你一次有哪些規則 |
| `claude-trust.json` | 你對各個專案的 Claude Code 設定做過的決定 | 全部的決定：在你重新確認之前，agent session 不會載入專案的設定 |
| `cards.json` | 哪些對話裡有選擇題和權限請求 | 之前問過的不會再顯示 |

對話裡原本顯示的選擇題、權限請求或建議如果因此不見了，網頁會顯示「主人的電腦已經不再保留這張卡片。」有五個檔案不能單獨
移到旁邊，只剩最後的辦法：`state.json` 和 `identity.key` 就是工作區本身，而其餘的狀態都指向 `agent-sessions.json`、
`topics.json` 和 `reports.json`（少了其中一個，主題會指向不存在的 session 和報告）。系統讀不了的紀錄檔（`audit.jsonl`、
`audit-text.jsonl`、`activity.jsonl`）也可以移走：那個檔案記的內容會失去，smurg 會重新開一個。

`~/.smurg/workspaces.json` 的 `shared` 裡，一筆資料長這樣（`workspaceId` 是工作區在 `~/.smurg/workspaces/` 裡的資料夾
名稱，`createdAt` 是一個整數）：

```text
{ "folder": "/Users/you/projects/my-app", "relay": "https://app.smurg.ai", "workspaceId": "ws_YOURCODE", "createdAt": 1791377829732 }
```

### 9.4 如果你照 smurg 0.5.0 的指示把狀態資料夾移走了

smurg 0.5.0 讀不了 0.4.0 分享過的工作區。它拒絕啟動，並要你把工作區的資料夾移走（`mv … ….old`）再重新分享。如果你
照做了，從那之後你用的就是一個新的工作區：工作區代碼相同，daemon 金鑰是新的，成員只有你自己。組員被問過金鑰是不是
換了，之前的邀請連結也都失效了。

你移走的資料夾還在：`~/.smurg/workspaces/<工作區代碼>.old`，裡面有成員、邀請連結和舊的 daemon 金鑰，smurg 0.5.1 和之後
的版本讀得了它。這樣的版本第一次啟動時，會在連結上面指出這個資料夾一次：「這個工作區之前的狀態資料夾還放在旁邊」。
換回去的方法：

```sh
smurg stop                                     # 1. 停止分享
cd ~/.smurg/workspaces                         #    （或你的 SMURG_HOME 裡的 workspaces 資料夾）
mv ws_YOURCODE ws_YOURCODE.new-workspace       # 2. 把目前使用的工作區移到一旁
mv ws_YOURCODE.old ws_YOURCODE                 # 3. 把之前的工作區放回原來的名稱
smurg host ~/projects/my-app                   # 4. 重新分享資料夾
```

`ws_YOURCODE` 代表工作區代碼：就是出現兩次的那個資料夾名稱，其中一個多了 `.old`。到第 4 步，`smurg host` 會讀取之前的
狀態、轉成現在的格式，並印出 §9.2 的那一行。兩個連結又帶著之前的 daemon 金鑰，資料夾被移走之前的成員又是成員，
裝置也和當時一樣。這也包括中間那段時間你沒有再邀請的人，角色和當時一樣：請在第 4 步之後到主人控制台把成員、角色和邀請
連結看過一遍（§9.2）。這個做法用 0.4.0 實際寫出來的工作區一步一步試過。

換回去之後，中間那段時間發生的事會這樣：

- 中間那段時間打開過新工作區的人，記下的是**新工作區的**金鑰：你自己的瀏覽器，以及每一位加入過它、或接受過它的金鑰的
  組員。他們不會被問任何問題，網頁會直接顯示「安全警告：已拒絕連線」（`smurg attach` 則是
  「…主人電腦的金鑰和這台電腦上次記錄的不同…」），只能靠連結繼續。你自己請打開第 4 步的「你的連結」。其他人請再傳
  一次連結給他們，並用其他管道把 `smurg status` 現在顯示的指紋告訴他們（就是移走之前的那一組）。打開連結之後，他們會
  被問「主人的電腦金鑰和之前不同」，比對指紋後再確認。
- 第 4 步印出的組員連結是「可編輯」的連結（除非你用 `--role` 選了別的角色）。原本是其他角色（「旁觀」、「可使用 agent」）
  的成員用了它，確認金鑰之後會看到「邀請連結無法使用」。其實金鑰已經被接受了：他不用連結，再打開一次工作區就進得去。
  你也可以在主人控制台幫他建立符合他角色的連結。
- 只加入過新工作區的人不是之前那個工作區的成員，中間建立的邀請連結在它裡面也不能用：請傳新的連結給他們。
- 中間那段時間的主題、對話和操作紀錄不會合併到之前的工作區。它們留在你第 2 步移到一旁的資料夾裡；那些主題的 spec、
  計畫和報告是專案裡的檔案，會留在原處。
- 那段時間的 worktree（分享資料夾裡的 `.smurg/worktrees/`）還留在磁碟上，但 smurg 不再認得它們：還要的修改請自己合併，
  再刪掉這些資料夾。
- 0.4.0 留下還沒處理完的東西又回來了：保留的 worktree 和裡面的工作，以及等你處理的合併請求，仍然可以檢視和核准。

還有兩件事要知道：

- 如果你把資料夾移走過兩次，第二次的 `mv` 不會取代第一個 `.old` 資料夾：它把被移動的資料夾放到裡面去，變成
  `<工作區代碼>.old/<工作區代碼>/`。之前的狀態是直接放在 `.old` 資料夾裡的那些檔案；做第 3 步之前，請先把裡面那個
  資料夾移出來。
- 如果你是特意把資料夾移走、為了換掉工作區的金鑰（§5.1「收回之後」第 1 步），就不要換回去：你想換掉的金鑰就在
  裡面。讓它留在原處，等不再需要裡面的對話和操作紀錄時再刪掉。

### 9.5 移除：`smurg uninstall`

```sh
smurg uninstall               # 列出會移除的東西，確認之後移除
smurg uninstall --keep-data   # 保留 ~/.smurg，只移除執行檔和快取
```

會移除：

- 執行檔本身（用安裝程式裝的是 `~/.local/bin/smurg`）；
- 快取：執行檔解壓縮出來的原生模組（macOS：`~/Library/Caches/smurg`；Linux：`~/.cache/smurg`；設定過 `SMURG_CACHE_DIR`
  的話是那個資料夾裡的 `native-…`）；
- 狀態目錄 `~/.smurg`（或 `SMURG_HOME`）：登入、裝置金鑰、每個工作區的金鑰、成員和邀請連結、agent session 的對話、
  紀錄檔。移除之後，分享過的工作區的成員和邀請連結都不再有效。`--keep-data` 會保留它。

不會動：

- **專案資料夾裡的 `.smurg/`**：worktree 和還沒合併的修改都在裡面。`smurg uninstall` 只把它知道的這些資料夾列出來，
  要不要刪由你決定。
- 你的主題的 spec、計畫和報告：它們是專案裡的檔案（分享資料夾裡的 `specs/`）。
- shell 設定檔：安裝程式只提示過要把 `~/.local/bin` 加到 `PATH`，沒有改過你的設定檔。你自己加過的那一行，請自己刪掉。

動手之前，它會列出每一個要移除的路徑和大小，並問「確定要移除嗎？ [y/N]」，輸入 `y` 才移除。`--yes` 不詢問；不在終端機裡
執行時必須加 `--yes`，否則它只列出內容就結束。正在分享的工作區會先停止（和 `smurg stop` 一樣）；停不下來就中止，什麼都
不移除。`SMURG_HOME` 指向不該刪的地方時（`/`、家目錄，或裡面有不是 smurg 建立的東西的資料夾），它會拒絕：這時用
`--keep-data`，再自己處理那個資料夾。

從原始碼執行 smurg 時：自己刪除上面三個位置。

## 10. 主題：主人要做的事

組員指南（那邊的 §6）說明一個主題從討論到團隊驗收成果的整個過程。這一節講的是一個主題需要你這位主人做什麼。

### 10.1 只有你能做的事

- **合併。** 合併由你作主：預設情況下，報告寫著完成且驗證過的工作項目由 smurg 替你合併，其他需要合併的會等你（§10.3）；
  沒有 git 時，工作項目會直接改動資料夾（§10.2）。工作項目要不要自動合併，是你的設定（「合併工作項目」）。
- **復原**合併過的工作項目或整個主題，在 smurg 有保存版本紀錄的地方（§10.3）。
- **決定只有你能決定的事**：改到只有你能合併的檔案的工作項目、沒有「可使用 agent」的成員手動改的檔案、擋住合併的主工作區
  （§10.3），以及沒有 git 時沒做完的工作項目的「就這樣接受」（§10.2）。
- **確認資料夾的 Claude Code 專案設定**（§5.3）、編輯 `CLAUDE.md` 和這些設定會執行的腳本，以及重新命名或刪除裡面有
  只有你能改的檔案的資料夾（§4）。
- **允許會動到專案以外的請求**、會寫到那些腳本所在位置的指令，以及自動模式下 smurg 對組員的 session 提出的請求（§5.2、
  §5.3）。
- **變更主人設定**（在主人控制台）：agent 不必先問就能做的事（工作區的權限模式，包括「什麼都不問」，§5.2）、工作項目要不要
  自動合併（§10.3）、同時可以有幾個 agent 工作（§10.4）、選擇題、請求或決定等多久之後也去問其他人（§10.6）、agent 能不能用
  你自己的 MCP 伺服器（§5.3）、要共用到 worktree 裡的資料夾。
- **沒有 git 時讓工作項目開始和再試一次**：這台電腦的 git 不能用時，工作項目會直接在分享的資料夾裡執行，只有你能讓它們
  開始（§10.2）。
- **session 連續三次啟動失敗之後再試一次**、終止任何 session、刪除已封存的主題、移除對話裡的某一則內容（§5.4）。

一個主題平常需要的事，你和每一位「可使用 agent」的成員都能做：建立主題、請 agent 產生計畫、按開始、回答權限請求、
暫停計畫和讓它繼續、略過一個工作項目，以及讓一個項目就這樣合併。agent 提出的選擇題由 session 的負責人決定；沒有指派負責人時，由開 session 或按開始的人決定；
身為主人，你隨時都可以送出答案。

### 10.2 開始：git，以及 smurg 做的提交

工作項目怎麼執行，要看資料夾和這台電腦的 git（2.42 以上）。在任何東西執行之前，開始對話框會說明是下面三種裡的哪一種：

- **是 git 儲存庫的資料夾**（至少有一個提交）：每個工作項目在那個儲存庫自己的 git worktree 裡執行，如下面所說。還沒有提交
  的儲存庫，或 git 不當成儲存庫的 `.git`，會讓開始停下來，並說明該怎麼做（§8）；要求使用自己的 worktree 的 session 被拒絕時，
  也是同樣的說明。
- **沒有 `.git` 的資料夾**：smurg 會在 `.smurg/git` 裡保存它自己的版本紀錄，絕不會在你的資料夾裡放 `.git`
  （「這個資料夾沒有自己的 git 儲存庫。smurg 會把資料夾現在的樣子記在它自己的版本紀錄裡（在 .smurg 裡，不是你的 .git），每個項目都從這裡開始。」），主題的工作和有儲存庫時一樣：每個工作項目一個
  worktree、結果報告的 diff、由你合併。
  - 開始時會把整個資料夾記進這份版本紀錄，以按開始的成員的名義；每個 worktree 都是它的一份副本。不會記進去的：`.smurg`
    本身、`node_modules/`、`.venv/`、`__pycache__/`、`.DS_Store`、不論在第幾層的組員看不到的檔案（§4）、共用到 worktree 的
    資料夾，以及資料夾自己的 `.gitignore` 忽略的東西。超過 1 GB 或 50,000 個檔案的資料夾，在寫入任何東西之前就會被拒絕
    （§8）：請把大的資料夾寫進 `.gitignore`，或設成共用的資料夾。
  - 資料夾裡如果有本身就是 git 儲存庫的資料夾（`frontend/.git`），它不會被記進去：工作項目看不到它，開始對話框會指出它
    （「這些資料夾各自是一個 git 儲存庫，工作項目看不到它們：…」）。要在其中一個裡工作，請分享那個資料夾。
  - 雲端服務同步的資料夾（iCloud 雲碟、`~/Library/CloudStorage` 底下的資料夾、Dropbox）裡，版本紀錄和每個 worktree 也都會被
    同步，只存在雲端的檔案可能讓開始失敗；對話框會說明。
  - **這份版本紀錄會保留它記下的每一個檔案的每一個版本，包括機密，你從資料夾刪掉檔案之後也一樣**，而 worktree 裡的 agent
    可以透過它自己的 worktree 讀到這份紀錄。它只會變大：smurg 會壓縮它，但絕不會清除。smurg 的檢查會讓別人碰不到它（沒有
    人能寫 `.smurg`，agent 指名它的編輯和指令都不會執行，而被別的程式改過的版本紀錄，smurg 會拒絕使用，§8）。
  - 資料夾之後變成儲存庫時，`.smurg/git` 會留著。等沒有任何屬於它的工作項目和合併請求在等時，你就可以移除它：之後在沒有
    `.git` 的資料夾裡按開始，會建立新的一份。
- **沒有 git 時**（找不到、版本比 2.42 舊，或無法執行）：工作項目會一次一個，**直接在分享的資料夾裡**執行，大家也在這個
  資料夾裡工作。改動生效之前沒有 diff 可以看，沒有東西會等合併，smurg 也無法復原任何改動。只有你能讓這樣的項目開始或再試
  一次，要先勾選對話框裡的確認（「我了解這些改動會直接寫進分享的資料夾」）；組員的對話框會顯示
  「沒有 git 時，只有主人能讓工作項目開始：它們會直接在分享的資料夾裡執行。」資料夾裡一次只有一個 agent 在工作，它之後的
  每一輪也一樣：另一個項目在工作時傳給某個項目的訊息會等待（「這則訊息在等待：另一個工作項目正在分享的資料夾裡工作，等它完成後才會送出」）。每個項目把報告寫在資料夾裡，沒有 diff。依賴某個項目的項目，要等它的報告寫著完成且驗證過（而且是在寫出它的那一輪檢查過的）才會開始；否則這個項目會等人決定：追問、「繼續」、「略過這個項目…」，或你的「就這樣接受」。報告被看過、或主題的成果驗收之後，它的 session 就結束了。要有 worktree，請安裝 git 2.42 以上的版本，再重新分享（§8）。
- 項目只會在它自己的開始選定的版本紀錄裡執行。那份版本紀錄不能再用時（git 不見了、`.git` 不見了或出現了、smurg 自己的
  版本紀錄被拒絕），這個項目不會開始，按「再試一次」也一樣，並且會說明原因（§8）；它絕不會自己換到另一份版本紀錄，或
  直接在資料夾裡執行。
- **資料夾可以在分享期間才變成儲存庫。** 在你自己的終端機，到分享的資料夾裡：

```sh
git init
git add -A                      # 請先為 node_modules 這類東西寫好 .gitignore
git commit -m "First commit"
```

- 每次按開始時，以及每隔幾秒，smurg 都會重新看一次：下一次的開始就會使用這個儲存庫，不必重新分享；開著的網頁也會在幾秒內
  看到。smurg 自己的版本紀錄建立的工作項目和合併請求，會繼續用它直到完成；新的則用這個儲存庫。git 本身有變動（安裝、更新、
  修好）時要重新分享：smurg 只在開始分享時和資料夾變成儲存庫時找 git，找的是執行 `smurg host` 的那個終端機的 `PATH`
  （§8）。在沒有 `.git` 的資料夾裡，smurg 自己檢查過 git 之前，不會為組員的請求執行 git（§8）。
- **git 不會收進 smurg 的 `.smurg`。** 每次開始分享時，如果沒有 `.smurg/.gitignore`，smurg 會寫一個（`*`），
  所以不論 `git init`、`git add -A` 和 `git commit` 的順序是什麼，git 都不會把這個資料夾放進去。如果儲存庫已經在追蹤它
  （用 smurg 0.5.1 或更早的版本分享時提交的），`smurg host` 會說一次；請把它移出儲存庫：

```sh
git rm -r --cached .smurg       # 檔案仍然留在磁碟上
git commit -m "Stop tracking smurg's own folder"
```

- 分享期間 `.git` 不見了，開始會被拒絕並說明原因，等著開始的項目可能要按「重新開始」（§8）。不會刪除任何東西：原來的
  `.git` 回來後，worktree、工作和合併請求都能再用。請把它放回去，不要改為執行 `git init`：新的儲存庫沒辦法合併那些
  合併請求。
- **開始之前會先顯示它要做的事**：哪些項目現在開始、哪些要等其他項目、每個項目由誰負責、上次開始之後誰手動編輯過 spec
  和計畫，以及下面說的提交。請讀過：這是團隊寫的文字變成 agent 的指示的那一刻，而這些 agent 是以你的身分執行的。它也會
  說明項目怎麼合併：由 smurg 合併（工作區的設定），或「每個項目都由主人合併」，按開始的人都可以選後者（§10.3）。成員
  重新命名或刪除了主題的資料夾（或 `specs` 本身）時，兩個檔案底下都會列出他的名字。smurg 以外的程式改了 `SPEC.md` 或
  `PLAN.md`，會照實列出來；整個資料夾被這樣的程式換掉時則不會列出來，不過 smurg 會馬上重新讀這兩個檔案，按開始時確認的
  就是它們當時的內容。
- **smurg 會替你提交 spec 和計畫**（在資料夾自己的儲存庫裡；用 smurg 自己的版本紀錄時，開始會記下整個資料夾，見上面）。
  worktree 裡只有已經提交的內容，所以有人按開始時，smurg 會提交剛好兩個檔案（這個主題的 `SPEC.md` 和 `PLAN.md`）到分享資料夾裡你目前簽出的分支（對話框會寫出分支名稱；smurg 會把項目合併到這個分支，而且只合併到這個分支），以按開始的那位成員的名義，
  訊息是 `smurg: spec and plan of <topic folder>`，並為每一位手動編輯過的人加上一行 `Edited-by:`。資料夾裡的其他東西
  不會被提交、暫存或更動，你的儲存庫的 git hook 也不會執行。儲存庫正在 merge 或 rebase 途中，或 git 忽略了主題的
  資料夾時，開始會被拒絕。
- **agent 只會從確認過的內容開始。** 要等其他項目的工作項目，會在它依賴的項目合併之後自己開始，而且只有在 spec 和計畫
  仍然和按開始時提交的完全相同時才會開始。之後只要其中一個檔案變了（「可編輯」的成員改了一個錯字、計畫更新了），這個
  項目就不會開始：按開始的人和你會在收件夾收到通知，看過變更之後再重新開始它。
- **每個工作項目有自己的分支** `smurg/<topic folder>/<item id>`（沒有 `.git` 的資料夾是 smurg 自己的版本紀錄裡的分支），
  worktree 在 `<資料夾>/.smurg/worktrees/` 底下。agent
  不會提交；結果報告寫好時，smurg 會以開始這個項目的成員的名義提交項目的變更，訊息是
  `smurg: work item <number> (<item id>)`。
- 全新的 worktree 裡沒有 `node_modules`，也沒有其他 git 沒有追蹤的東西。可以在主人控制台的設定裡指定要共用到每個
  worktree 的資料夾（在 worktree 裡對人是唯讀的），或讓 agent 先安裝。

### 10.3 合併，以及什麼在等它

合併由你作主。預設情況下，你給了 smurg 一項長期的同意：主人控制台設定裡的「合併工作項目」寫著
「報告寫著完成且驗證過的，由 smurg 合併」，工作項目沒有問題時，smurg 會替你把它合併到主工作區，不會先有人讀過 diff。
想要每個項目都自己讀過再合併，請在那裡選「每個項目都由我自己合併」（見下面）。關掉會立刻生效（已經在進行的合併會做完），
所有已經開始的工作項目都改由你合併，而且不會再改回去；打開則從之後開始的工作項目起生效。

- **完成且驗證過**是報告的說法：它的結果是「完成」、至少一項驗證通過，而且沒有驗證失敗。驗證是 agent 自己報告的：smurg 不會
  執行它們。打勾的方框是 agent 說這項驗證通過了：常見的自相矛盾 smurg 會拒絕（打勾的驗證寫著 `failed`、`not run`、
  `not verified`、`fails`、測試工具的 `FAIL` 或 `FAILED`、`失敗`、`未驗證`，或失敗、錯誤的數目，例如 `2 failed`、
  `2 個失敗`），agent 會重寫那一行；其他的說法它讀不出來，能抓到這些的是團隊最後的驗收和復原。報告列為未驗證的項目不會擋住
  合併；成果那一欄會先列出它們（見下面）。
- **smurg 什麼時候會自己合併一個項目**：它的這一輪正常結束，之後也沒有哪一輪被停止；它的報告之後沒有人對它的 agent 說過話；
  報告是目前的版本，agent 在寫出它的那一輪檢查過（沒有的話 smurg 會請它檢查一次：「正在重新檢查報告」），而且寫著完成且驗證過；
  沒有「可使用 agent」的成員沒有手動改過它的檔案；這個項目沒有任何東西在等人；smurg 的合併規則允許它的檔案（見下面）；沒有人
  提出它的合併請求（有人提出的合併仍然由你決定）；主工作區在它的開始提交的那個分支上，而且沒有已暫存的東西；合併本身也很順利。
  smurg 在 `git merge` 執行之前會把這些再看一次：先來的「暫停」、關掉設定或「略過這個項目…」會先生效。一次只合併一個，最早的
  報告先合併；等著某個項目的項目，會從合併後的主工作區開始。
- **合併**是那個分支上的一個提交，作者是你（這是你的同意），提交者是 smurg，訊息是
  `Merge smurg/<topic folder>/<item id> (<name>)`，最後一行是 `Merged-by: smurg (automatic merging, the host's setting)`
  （沒有 `.git` 的資料夾，則是在 smurg 自己的版本紀錄裡一樣這樣做）。操作紀錄會記成「smurg 替你合併了一個工作項目」，並寫出
  這是你選的設定，還是更新設定的（§9.2）。smurg 絕不會合併到別的分支上：在 detached HEAD 上按的開始由你合併，對話框也會說明
  （「主工作區不在任何分支上（detached HEAD），所以這次開始的每個項目都由主人合併。」）。
- **合併不順利時。** 另一邊只有其他工作項目的變更時，smurg 會自己讓這個項目的 worktree 跟上主工作區（agent 不會執行 git，
  也不會用到你的 git hook 和 git 設定），再請這個項目自己的 agent 解決並重新驗證（「正在跟上主工作區」）；它的下一個版本會
  和第一次一樣再試著合併。試了三次之後就是一個決定。另一邊是某個人的修改時（你的、組員的，或在 smurg 以外做的提交），
  會立刻成為一個決定，並寫出檔案和是誰改的：smurg 絕不會讓 agent 自己蓋過人寫的內容。worktree 裡 git 沒有追蹤的檔案
  絕不會被覆蓋。
- **自己會等的**：有人正在打字的檔案（「等著合併：Amy 正在編輯」），以及主工作區的 git 正在忙一下子。**會等你處理、處理完
  就會自己繼續的**：合併要動到的檔案有還沒提交的修改、項目要新增檔案的位置上有檔案擋住、有已暫存的東西、主工作區在別的分支
  上、那裡的 git 已經忙了十分鐘、有一次復原被中斷了。那些檔案或 git 有變動時 smurg 會再看一次，最晚每分鐘一次；每一種該怎麼
  做，見 §8。
- **什麼會停下來，由誰決定。** 一個決定只會讓它的項目和依賴它的項目停下來，其他的會繼續。它是收件夾裡在等人的一項
  （「… 沒有合併：…」），項目的底部會寫出原因和每個人可以做什麼，§8 每一種原因都有一列。報告不是完成且驗證過、有衝突、
  報告之後有人對 agent 說了話或之後的一輪被停止：項目的負責人有「可使用 agent」時由他決定，否則由你和「可使用 agent」的成員
  決定，過了等待時間（§10.6）之後你們都可以決定。只有你能決定的：改到只有你能合併的檔案、沒有「可使用 agent」的成員手動改的
  檔案、擋住合併的主工作區。一個決定可以做的事：「請 agent 修正」（在報告下面追問）、「請 agent 解決衝突」、
  「就這樣合併」（這個版本就這樣算數）、「繼續」、「請 agent 拿掉它們」和「合併…」（你），以及「略過這個項目…」。「可編輯」的
  成員給工作項目的 agent 的建議（在報告下面追問，或在它的對話裡傳的訊息）也是一個決定：它等的是同樣的人，過了等待時間之後
  你們都會收到，在有人接受或拒絕它之前，主題不會待驗收。
- **「略過這個項目…」**（你和「可使用 agent」的成員）不用改計畫，就把一個項目和依賴它的每個項目略過：它們的變更不會合併，
  它們的 session 會結束，worktree 會保留。
- **smurg 自己要求的那幾輪**（解決衝突、重新驗證、重新啟動、用量限制或錯誤之後繼續）是在沒有人看著的情況下執行的，用的是項目
  自己的權限模式：它改的檔案留在自己的 worktree 裡，它的指令能碰到的範圍和任何一輪一樣（§5.2）。
- **待驗收。** 每個項目都合併了而且沒有東西還在進行、或被略過、或被復原之後，主題就是「待驗收」：每位成員的收件夾都會顯示
  「待驗收：<主題>」，開著的網頁會跳出通知，`smurg host` 會印出一行：

```text
主題「Checkout」待驗收：3 個工作項目中有 3 個已合併到分享的資料夾。請到工作區查看成果。
```

- 主題的「成果」欄會顯示合併了幾個項目、幾項驗證通過、失敗或未驗證，先列出未驗證的，再列出每個項目改過的每個檔案和
  smurg 合併它時的 diff、要注意什麼，以及每個項目和它的報告。各自順利合併的項目，還是可能彼此弄壞：在最後之前，沒有任何
  東西驗證合在一起的結果。看過成果（在主工作區自己跑一次專案的測試），再由「旁觀」以外的任何人按「我已驗收」：主題就完成了，
  工作項目的 session 也會結束。在那之前，從報告追問仍然會送到做這件工作的 agent，它改的東西也會和第一次一樣合併。
  「我已看過」仍然是每份報告上的一個標記：它不會改動資料夾裡的任何東西。
- **復原和它的限制**（只有你）：在 smurg 有保存版本紀錄的地方（資料夾自己的 git，或 smurg 自己的版本紀錄），合併過的項目上有
  「復原…」，成果那一欄有「復原整個主題…」。smurg 會先顯示這次復原會做什麼，不會動到資料夾：在它之上做的項目會一起復原，之後
  改了同樣幾行的合併也會（不論是哪個主題的，都會寫出它的主題，它們的 session 也會結束）；依賴它、還在執行的項目，之後在同樣
  幾行有人做的修改（會寫出是誰）、有人正在打字、動到的檔案有還沒提交的修改、有已暫存的東西、git 正在忙，或在別的分支上，都會
  讓它不能執行；被復原的項目的 worktree 裡有沒被任何合併帶走的變更（某位成員在那裡存檔的修改、它的 agent 之後的回合做的）也會：
  復原會把它們刪掉，所以要先讓它們合併，或由你刻意移除那個 worktree。之後由一個新的提交（以你的名義）把變更拿掉；報告和對話
  都會留著，被復原的項目可以再開始。在 smurg 自己的版本紀錄裡，會先把資料夾記下來，所以不會拿掉任何人已經存檔的修改。復原進行時
  有成員在 worktree 裡存檔，那個 worktree 不會被刪掉：它會留下來成為它的擁有者的 worktree，項目再開始時會用新的一個。smurg 已經
  沒有保存合併紀錄的項目（它的 worktree 已經移除，而 smurg 只保存最近 300 個已決定的合併）在這裡無法復原（「smurg 在主工作區的
  版本紀錄裡找不到這個項目的合併了。」）：請在你的終端機用 git 把它 revert。復原拿不回來的：agent 的指令在這個資料夾以外做的事（別的
  資料夾、安裝的工具、它呼叫過的服務），以及你已經推送的分支，要等你也推送這次復原，那裡的合併才會拿掉。在資料夾自己的 git
  裡想把復原的變更找回來，請在你的終端機對那個復原提交執行 `git revert`。沒有 git 時沒有東西可以復原（§10.2）。
- **smurg 絕不會自己合併的檔案**：只有你能改的檔案（`CLAUDE.md`、`.claude/`、`.envrc` 這類，以及你確認過的專案設定會執行的
  腳本，§5.3）、主題自己的 `SPEC.md` 或 `PLAN.md`、指向專案以外的連結，以及 smurg 的 `.smurg`。這樣的項目會列出這些檔案等你
  處理：「請 agent 拿掉它們」，或自己提出合併請求，讀過 diff 再決定。報告會說明原因，例如
  「無法顯示變更：worktree 裡有只有主人可以修改的檔案」
- **組員手動改的檔案**：「可編輯」的成員在工作項目的 worktree 裡改的檔案會等你
  （「沒有合併：Amy 手動改了它的檔案」）；用「合併…」讀過 diff。有「可使用 agent」的成員本來就能讓 agent 做同樣的修改，所以
  他們改的會和 agent 的一起合併。
- 每個人都能讀報告的 diff 和成果那一欄。組員看不到的檔案（§4）在那裡只列出檔名、不顯示內容（你除外），看起來像登入資料的
  文字對所有人都顯示為 `[masked]`。
- **項目什麼時候算完成**：已經合併而且看過、或它的主題已經驗收的工作項目，等它的 worktree 裡沒有還沒合併的東西、它的 agent
  也不在某一輪當中（回應某則訊息的那一輪會先做完，它改的東西會成為它自己的版本；之後的一輪沒有做完時，smurg 會照 §10.5 說的
  自己繼續（就算你在那之間合併了它），否則它會等人按「繼續」，在那之前主題不會待驗收；它的 session 結束了，就不再等那一輪），
  就完成了：它的 session 結束，worktree 被移除，對話和報告仍然讀得到。在那之前它的 session 和 worktree 會留著，讓從報告追問
  的問題送得到做這件工作的 agent。
  smurg 合併過的項目，它的 worktree 裡有任何一次合併都沒有帶走的變更時（有成員在那裡存了檔、它的 agent
  在報告之後執行的指令改了檔案、之後的一輪沒有做完），這個項目會等它的負責人決定：「已合併；之後的變更沒有合併：…」，「繼續」
  會把這個變更做成它自己的版本，和第一次一樣合併。worktree 正在被移除時（例如按了「我已驗收」）有成員在裡面存檔，那個檔案不會
  被刪掉：這個 worktree 會留下來成為它的擁有者的。封存主題時，會列出變更從來沒有合併的工作項目，並問你要保留還是刪除。
- **每個項目都由你自己合併時**（設定選了「每個項目都由我自己合併」、按開始時選了「每個項目都由主人合併」、在 detached HEAD
  上按的開始，以及更新到 0.7.0 之前就開始的每個工作項目）：
  - 結果報告被看過之後，它的變更會自己出現在你的收件夾裡，顯示為
    「已看過，可以合併」，並列出等著它的項目。「可使用 agent」的成員也可以請你合併還沒有人看過的工作。
  - 點收件夾裡的那一列，會打開這個項目的結果報告。那裡的「合併…」會顯示完整的 diff；你讀過之後，再選「合併到主工作區」
    或「拒絕」。（報告之後才有人提出的請求，或沒有報告的 worktree 的請求，打開的會是它的變更清單，選項一樣是這兩個。）合併的
    提交是你的，並寫明是誰的工作（`Merge smurg/<topic folder>/<item id> (<name>)`：提出合併請求的成員，沒有人提出時是
    開始這個項目的人）。它會合併到主工作區現在所在的地方。
  - **依賴其他項目的工作項目，要等你合併那些項目之後才會開始。** 在這樣的計畫裡，大家等的就是你：計畫會顯示哪些項目在等
    合併，收件夾會把能讓其他項目開工的合併排在前面。
  - **有衝突**時合併會停下來，主工作區維持原樣。你或「可使用 agent」的成員可以請這個項目的 agent 解決（「請 agent 解決衝突」），
    它的新報告被看過之後，會再次提供合併。
  - 你合併之後有人追問、agent 又多改了一些：新的變更和第一次一樣等你合併（「已看過 · 等主人合併」）。
- **沒有 git 時**沒有東西要等合併（計畫會顯示「沒有 git 時，工作項目會一次一個直接在分享的資料夾裡執行；沒有東西要等合併。」）：
  項目的報告一進來、而且寫著完成且驗證過，就算合併了，依賴它的項目等資料夾空出來就會開始。否則就是一個決定，你也可以按
  「就這樣接受」（§10.2）。

### 10.4 同時有幾個 agent 工作，以及記憶體

- 每個正在工作或在等人回應的 agent 各有一個 Claude Code 程序。在開發用的電腦上，剛啟動的一個約用 260 MB 記憶體，對話
  很長的一個用 400 到 600 MB。
- 所以 smurg 會限制同時工作的工作項目數量：預設 8 個，記憶體少的電腦更少（大約每 3 GB 一個，至少 2 個）。上限在主人
  控制台的設定裡改（「同時執行的工作項目數量」）。在等空位的工作項目會在計畫裡這樣顯示，並寫出工作中的 agent 有幾個
  在等人回應。
- 待命的 agent 過一陣子會放掉它的程序，下一則訊息來時再啟動一個；對話會從原來的地方繼續。在等回答或等許可的 agent
  會留著它的程序。這些在等的工作項目不會擋住不相關的項目開始：這時同時存在的程序最多可以到上限的兩倍（而且絕不超過
  32 個），所以沒有人處理的收件夾可能讓 agent 用掉的記憶體變成兩倍。這台電腦負擔不起的話，請把上限調低。
- smurg 不顯示 token 數，也不顯示費用。好幾個 agent 同時工作，用掉你 Claude 帳號用量的速度就是一個的好幾倍；用量請到
  你的 Claude 帳號顯示它的地方看。

### 10.5 重新啟動之後：什麼會自己繼續

`smurg host` 停止後再啟動（當掉或電腦重新開機之後也一樣），計畫會自己繼續：

- **在任何東西繼續之前**，`smurg host` 會在連結下面印出哪些主題會繼續：

```text
2 個主題從停下的地方繼續：Checkout（2 個工作項目）、Search（1 個）。要暫停其中一個，請在它的計畫裡按「暫停」。
```

- 接著被中斷的 agent 會被告知繼續（它的對話裡會顯示「主人電腦上的 smurg 重新啟動過，它請 Claude 繼續」），在等待的工作項目會在
  可以開始時開始，smurg 也會合併沒有問題的項目。重新啟動之前還開著的選擇題或權限請求，會在它的 session 繼續時再問一次；之前
  那張卡片的投票和留言仍然讀得到。
- **停止的時候**（Ctrl-C，或 `smurg stop`），它會說下次啟動時有幾個主題會繼續：

```text
下次 smurg host 啟動時，2 個主題會自己繼續。要讓計畫保持停下，請在停止 smurg host 之前，先在計畫裡按「暫停」。
```

- 計畫裡的**「暫停」**（你和「可使用 agent」的成員）是重新啟動之後也會留著的煞車：在有人按「全部繼續」之前，不會有新的項目
  開始，也不會有東西自己合併或繼續。正在執行的那一輪會做完，已經在進行的合併也會做完；要讓正在工作的 agent 停下來，請停止它的
  session。如果你要因為某個 agent 做了不該做的事而停止 `smurg host`，請趁 `smurg host` 還在執行時先暫停它的計畫：它停止的
  期間沒有人能暫停任何東西（網頁上的「暫停」和「全部繼續」會關閉），下次啟動之後繼續的那幾輪是在沒有人看著的情況下執行的
  （§10.3）。
- **報告已經交出的工作項目，它被停止打斷的後續回合**（某人傳給它的 agent 的訊息、後續追問）不會被告知繼續：啟動之後已經不知道
  那一輪被要求了什麼。傳給這樣的項目、還沒有任何一輪接手的訊息也一樣：它會留在 session 裡等著。這個項目會等它的負責人決定
  （「它的上一輪沒有做完」：繼續、「就這樣合併」或「略過這個項目」；已經合併的項目則是繼續，它已經合併的版本會留在資料夾裡），
  在那之前它的任何東西都不會合併。這樣的訊息還在等的時候，不會出現「就這樣合併」（沒有 git 時也不會出現「就這樣接受」）：要先
  按「繼續」把它送出去。你看過整個變更之後，你自己的「合併…」仍然由你決定：那個版本會合併，之後這個項目會像已經合併的項目一樣
  等人按「繼續」。你自己合併的項目（§10.3）也一樣，在它等著的時候你關掉了 smurg 的合併也是。在按下「繼續」之前，主題不會待驗收，
  「我已看過」也不會結束這個項目的 session。已經合併的項目按了「結束 session」，那一輪就不算了：它改的東西留在 worktree 裡，在
  那裡按「請求合併」會把它放進你的收件夾。你拒絕了，它就不算了（仍留在那裡）；你拒絕過的後續版本，「結束 session」之後也一樣。
- 重新啟動之後**有兩種計畫會維持暫停**：有人暫停的（`smurg host` 會寫出它：「有人暫停、仍在暫停中的主題：…」），以及有直接
  在分享的資料夾裡執行、被中斷的工作項目的（它做到一半的變更就在沒有版本紀錄的資料夾裡）。網頁會在 session 畫面的最上面顯示
  後者（「主人電腦上的 smurg 重新啟動了。」），你和「可使用 agent」的成員每個主題會有一個收件夾項目。「全部繼續」讓這樣的
  計畫繼續。
- 其他的中斷之後，smurg 也會自己繼續，每一種都有次數上限：你的用量限制重置之後、某一輪因錯誤結束之後（兩次：一分鐘後和五分鐘
  後）、agent 的程序停止之後（一次，一分鐘後），以及它沒能記下項目的變更之後（一次）。有人停止的項目、計畫暫停時，或 Claude
  Code 登出時，都不會。在那之前不會有人被問到它（用量限制仍然是你收件夾裡關於帳號的那一項）；次數用完之後，這個項目會等它的
  負責人處理。已經合併的項目也一樣，不論是誰合併的。

### 10.6 有人沒有回答、離開或被移出時

- **沒有人回答。** 選擇題或權限請求等了超過等待時間（預設 5 分鐘；可以在主人控制台的設定裡設成 1 到 60 分鐘），或該
  回答的人已經離線一分鐘，它也會出現在你和每一位「可使用 agent」成員的收件夾裡。這時你可以代那個人回答
  （「代 Ian 送出」）；對話會記下是你代為回答的。沒有合併的工作項目的決定，也會這樣送到你和他們那裡（§10.3），只有你能處理
  的決定除外，那些從一開始就是你的；agent 沒能做完的工作項目（沒寫報告就停下、程序失敗，或被停止），以及「可編輯」的成員給
  工作項目的 agent 的建議，也一樣。你自己合併的項目的結果報告沒有人看過時，過了六倍的時間之後也一樣。
- **成員離開工作區，或你改了他的角色**，讓他不能再使用 agent：他的終端機和不屬於主題的 agent session 會結束。主題的
  session 會轉給你並繼續執行（「Amy 已離開，這個 session 改由主人接手」）。他離開了、或現在是「旁觀」時，原本由他負責
  的事改由下一個人決定：開 session 或按開始的人，或是你。改成「可編輯」的成員仍然負責他原來負責的事。結束的那些 session
  的 worktree 會連同裡面的修改保留下來。改角色之後，它們會轉給你。自己離開的成員則留著他的 worktree：離開不會拿掉角色，
  他再打開工作區時還找得到它們。
- **你移出一位成員**：一樣，但他的主題 session 會先被停止
  （「Amy 已被移出，這個 session 已停止，改由主人接手」），他保留下來的 worktree 也會轉給你。被移出再重新加入的成員，
  不會拿回他原來的 session。
- 這幾種情況下，他設定的東西都會跟著他一起消失：他設為一律允許的指令類型會被移除，他選的權限模式，除非比 session 或主題
  原本會跟隨的更嚴格，否則會改回去（更嚴格的會留著），他選的可能從用量額度扣款的模型會改回你的預設（對話裡會顯示
  「模型已恢復為主人的預設：…」），他開始但還沒開工的工作項目要等有人重新開始才會開始。轉給你的 session 保有它建立時的限制：它的 agent 還是不能改
  只有你能改的檔案。

### 10.7 很長的討論

主題的討論是所有人共用的一段對話，可能會變得很長。

- 放不下的時候，Claude Code 會自己縮短較早的部分（看得到的一段停頓，然後顯示
  「Claude Code 為了騰出空間，縮短了較早的對話內容。」）。spec 和計畫是檔案，所以已經決定的事不會不見。
- 對話越長，每一輪的花費越高；團隊自己討論了一陣子、agent 沒有動作之後，下一輪會把整段對話重新讀一次，算在你的帳號上。
- 所以很長的討論會提供「開始新的對話」：主題會有一段新的討論，從目前的 spec 和計畫開始。之前那一段仍然讀得到。
- 如果主題的討論完全不能用了（被終止了，或連續三次啟動失敗），你和建立主題的人會在收件夾收到附有「重新開始討論」的
  項目。檔案和工作項目不會因此被更動。

### 10.8 驗證過什麼，還沒驗證什麼

這個版本的流程（附選擇題與投票的討論、spec、計畫、工作項目、結果報告、由 smurg 合併、決定、待驗收、復原、重新啟動）是 smurg
的開發者用一個照劇本回應的模型替身驗證的。真正的 Claude Code（2.1.288 版，也就是 agent session 接受的最舊版本）只在開發用的電腦上、對著假的 API
和 smurg 一起執行過，從來沒有對著真正的模型執行；測試時也沒有使用任何真正的 Claude 帳號。那台電腦是 Mac：這個版本完全
沒有在 Linux 上搭配真正的 Claude Code 執行過，Linux 上只測試過替身。
所以真正的模型在這個流程裡的表現還沒有驗證過：它會不會照指示用卡片提出選擇題、會不會用 smurg 檢查的格式寫計畫和報告、
提出的分工合不合理。這些可能需要在之後的版本調整。

0.6.0 的模型和權限模式也是用同樣的方式驗證的：用照劇本回應的替身，以及真正的 Claude Code 2.1.288 對著假的 API，連自動模式的
檢查都是由假的 API 回答。所以真正的檢查怎麼判斷一個指令，以及可能改在 Anthropic 那邊執行的檢查，都從來沒有和 smurg 一起
看過；這裡也沒有使用任何真正的帳號。第一次用自動模式時，請留意 agent 執行了什麼。

0.7.0 的自動合併、決定、復原和重新啟動也是用同樣的方式驗證的：用替身，以及真正的 git（開發用的電腦上是 2.49）。真正的模型
會在報告裡寫什麼（是不是只有在工作做完時才寫「完成」、沒有通過的驗證會不會寫成失敗），決定了 smurg 會不經人讀過就合併
什麼，而這從來沒有看過。前幾個主題的報告和合併請仔細看著，在你信得過之前，可以先關掉自動合併（§10.3）。

agent 不照規矩來的時候，損害有限的原因：smurg 會自己檢查計畫和報告的格式，並請 agent 修正（最多連續兩次）；報告沒寫
時會再請它一次；停下來的工作會放進某個人的收件夾，而不是沒有人知道地停著。第一次用真正的專案開主題時請仔細看著，
如果流程的某一步在你的 Claude Code 上行不通，請到 https://github.com/gclinian/smurg 回報。

這個版本已知的限制：

- agent 不會啟動 subagent，`.claude/agents` 裡的 agent 定義也不會被使用（§5.2）。
- 結果報告裡的驗證，是 agent 說它做了的：smurg 一項都不會執行。各自順利合併的工作項目還是可能彼此弄壞，而在主題待驗收之前，
  沒有任何東西驗證合在一起的結果（§10.3）。
- 自動模式的檢查是模型的判斷。自動模式下 smurg 自己的檢查只看得到它讀得出來的指令內容，它的拒絕規則也只拒絕指名某個地方的
  指令（§5.2）。smurg 還靠 Claude Code 2.1.288 做到這些：session 的設定檔只在啟動時讀一次；拒絕規則在自動模式和「什麼都不問」
  下都會拒絕指名它那個地方的 shell 指令；不經檢查的那條路只涵蓋 agent 自己資料夾裡的指令。smurg 每驗證一個新版的 Claude
  Code，都會先再檢查這些事。
- 沒有 `.git` 的資料夾的 smurg 自己的版本紀錄只會變大，也會保留你刪掉的檔案（§10.2）。
- 模型清單是你的 Claude Code 最近一次回答的內容；之後從你的帳號拿掉的模型，在 session 裡會顯示為被拒絕（§8）。
- 專案設定會執行腳本的資料夾裡，smurg 讀的是 agent 的 shell 指令提到了什麼。完全沒提到這些腳本的程式（建置、會改寫另一個
  腳本的腳本），在執行之前是看不到的（§5.3）。
- 移除對話裡的一則內容，不會移除存有同一段文字的卡片、收件夾摘錄和操作紀錄（§5.4）。
- agent 或成員寫的連結，要把滑鼠停在上面、或用鍵盤移到它上面，才看得到它連到哪裡。連結的文字本身寫的是另一個地方時，
  smurg 會把目的地直接寫在文字旁邊（`github.com (https://evil.example/)`），但不是每一種情況它都認得出來：結尾比較少見的
  名稱（`amazon.in`、`github.lol`），以及裡面有個只是長得像句點的符號的名稱，都會畫成一般的連結。點連結之前請先看它的
  目的地（組員指南 §5）。
- 排版要花太久的 spec 或訊息，會整份或其中一部分照原樣顯示，上方有一行說明。在這樣一份很大的 spec 裡打字，最初的幾下
  按鍵可能每一下都要將近一秒，直到每個排版很慢的段落都被擱到一邊為止。
- agent session 結束、或你停止分享時，smurg 會結束 agent 的指令留著在跑的程式。在 macOS 上有一種程式可能漏掉：Apple 自己的
  程式（`/bin/sleep`、`/usr/bin/python3`）的背景工作，而且啟動它的 shell 馬上就結束了。這種工作，只有在 smurg 每兩秒一次
  的掃描剛好在 shell 還在時看到它，才找得到。`node`、`pnpm` 或 Homebrew 的 `python` 都找得到。
- 主人只能用 macOS 或 Linux，不支援 Windows；組員只需要瀏覽器，用什麼作業系統都可以。在 Linux 上，全部測試都通過（Ubuntu
  24.04：arm64 虛擬機，以及 GitHub Actions 的 x64），但還沒有人真的在 Linux 上當過主人：除了真正的 Claude Code（見上面），
  安裝程式也還沒在全新的 Linux 電腦上跑過。
- 只有 Apple Silicon 的執行檔在開發用的電腦上測試過；Intel Mac 與 Linux 的執行檔由 GitHub Actions 在各自的平台上建置，
  並在那裡跑冒煙測試。
- 還沒有做的：針對 spec 某一段的留言、費用或 token 數字，以及 agent 對話的終端機介面（`smurg attach` 只能接上終端機
  session：組員指南 §10）。
